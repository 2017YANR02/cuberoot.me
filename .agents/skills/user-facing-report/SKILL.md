# 面向用户的展示报告

让用户在常见桌面窗口的一到两屏内看懂：是什么、结果如何、有什么边界。通过筛选内容和统一排版缩短页面，不靠缩小字体或隐藏不利结果。

## 先判断读者与页面职责

- 结论展示页优先给结果与具体例子；功能入口优先给操作；教程和参考资料允许长篇，先检查导航、检索和分节是否清晰。
- 用户只说审查、列清单或先不改时，只取证和提出建议；不修改被审查页面。
- 同一任务中保留既有数据来源、原始精度、语言支持和入口。不要为排版重新运行昂贵计算，也不要手抄结果另造事实源。

## 内容取舍

推荐顺序是短标题与一句摘要 → 核心结果 → 一两个必要例子 → 适用边界。根据实际问题删减，不为凑结构增加区块。

- 第一屏回答用户的问题，删去页面自我介绍、标语、显然的操作提示、重复总结和实现过程。
- 同类信息用一张紧凑表格对齐；没有增加理解的卡片、进度条、大数字和分栏不用保留。图表只有在比文字或表格更好理解时才用。
- 用具体结果替代“领先、极致、全面”等评价。先给通俗含义，再按需解释术语，不把代码变量、哈希、部署细节放进主要阅读路径。
- 相同指标不要在 hero、大数字、图表、正文中重复四遍。例子保留能看出差别的条件与结果，省略内部用例 ID。
- 版本、完整分组、原始数据、计算公式、历史迭代和复现命令可放在命名明确的折叠区或附录；下载与来源仍可找到。

## 公平与准确

- 对照必须说明相同条件、版本和评价口径。优势、较差结果、最大误差及影响理解的局限一同呈现，不用折叠区藏起不利结论。
- 区分模拟、软件回放、真机测量与生产环境；用例中的比例不是现实故障率，单个案例不能推出全局精度百分比。
- 展示位数按读者需要取舍；取整或近似需明确，原始数据与计算值不变。避免用无实质意义的小数差营造优势。
- 无法核实的结果标出待验证，不为文案完整补造数字。

## 排版基线

- 默认单列，正文宽度约 720–840px，标题、段落和表格共用左边线。不要给几行说明加大面积空白。
- 正文优先 18px；表格、说明和控件通常 16–17px。版本哈希可略小，但不把关键解释降成 11–13px 脚注。
- 标题只保留必要层级，间距一致；优先留白与细线，避免装饰性编号、大底框、重复卡片和多种强调色。
- 窄屏自然换行，保留字号和完整内容；不裁切、固定高度或靠页面内部滚动强行凑屏数。
- CubeRoot 中复用现有返回、语言/主题、折叠和链接组件；文案与颜色遵循 `i18n`、`theme-tokens`。新增路由/标题再按 `document-title` 处理，不另造页面设计系统。

## 验证与交付

- 在实际浏览器检查默认折叠状态，记录窗口尺寸和页面高度，确认是否接近一到两屏。检查第一屏能否读到结果，最后一屏是否能看到局限。
- 看中英文、手机排版和主题切换；特别检查英文增长、表格换行、过小字号及横向溢出。不要为好看的截图调整缩放或隐藏页面内容。
- 只做与改动相称的验证。纯文案/样式不用重新跑计算基准；涉及统计或交互变化时再验证对应行为。
- 对只读扫描，先做全站路由/源码初筛，再浏览候选页面。区分“浏览器确认”与“仅源码候选”，不能用文件长度或页面高度直接判定内容冗余。清单给出页面、具体问题、优先级与建议，不冒充所有动态内容都已验收。
- 提交与发布沿用用户授权，展示完成后的真实截图。不要在回复里再写一份冗长的改版报告。
