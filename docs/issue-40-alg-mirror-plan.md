### 1.3 mid-AUF:实测结论 —— 「再商一次」这个口径不是良定义的不变量

> 本节全部由 `packages/client/scripts/lsll-class3.mts` 实证,不是推测。跑一次约 20 秒。

**先把对的结构立住**(脚本逐项验过,全中):

| 量 | 值 | 校验 |
|---|---|---|
| ZBLS 构型空间 \|Φ\| | 1,200 | 定义式枚举 |
| ZBLS case = Φ / pre-AUF | **306** | DB 的 zbls 恰好 305 = 306 − 全解态 ✓ |
| pre-AUF 轨道谱 | 297 自由 + 3 个 \|Stab\|=2 + 6 个 \|Stab\|=4 | 4·297+2·3+6 = 1200 ✓ |
| 每个 fiber ≅ ZBLL 空间 | 7,776 | = 9,331,200/1,200 ✓ |
| fiber 上 mid+post 双侧商 | **494** | = 通行的 ZBLL 493 + 全解态 ✓ |

**再说为什么给不出唯一的精确值。** pre 和 post 是状态空间上的规范作用(右乘 / 左乘 U)。mid 不是:它是「做完 ZBLS 公式之后」的转顶层,在 s 空间里的作用等于右乘 `W·U⁻ᵏ·W⁻¹`,**W = 所选的那条 ZBLS 公式**。换公式,mid 的作用就换。

对 297 个**自由**构型,pre 被完全吸收,fiber 内只剩 mid+post,贡献恒为 494 —— 与公式选择无关。对 9 个有 pre-AUF 对称的构型,stabilizer 会在 fiber 上多诱导一个「右乘 V = Z⁻¹UᵏZ」,而 V 直接依赖 Z。实测(同一构型、同样合法的公式,只在尾部接一条 ZBLL 群元素):

```
O/I  Z = F R U R' U' F'                      → 轨道 19
               Z = F R U R' U' F' + Sune               → 轨道 62
               Z = F R U R' U' F' + T-perm             → 轨道 89
D+/D L         Z = U F' (L' U2 L U')2 F                → 轨道 127
               Z = 同上 + U-perm                        → 轨道 494
```

**所以「商掉三个 AUF」这个口径不产生规范的 case 数。** 它的形状是:

- **硬部分(与任何选择无关)**:297 × 494 = **146,718**
- **严格区间**:∈ **[147,220, 151,164]**(9 个对称构型每个 ∈ [1, 494];全解构型恒为 494,因为那里 Z = 恒等、mid 与 pre 重合)
- **当前站内 zbls 公式库这一实例**:**147,508**
- **issue 的估算 583,284/4 = 145,821 一定偏小** —— 真值必然大于它,原因是 pre/mid/post 三者不构成自由的 (Z₄)³ 作用。

### 1.3c 良定义的三类:不商,而是乘 = 306 × 494 = 151,164

上面那个口径的毛病是把 mid 硬塞成「局面之间的等价关系」。**局面是死的** —— 你插不插那一下 U,魔方一动不动;mid 发生在**解法**上。两步解法里真正在变的是**一对图**:先认出一个 ZBLS case,做完之后看到一个 ZBLL case。两个集合各自规范,于是

> **N₃ = 306 × 494 = 151,164**(扣掉「全部已解」那格 = 151,163)

每个组合都真会出现(固定任一条 Z_φ,它的 fiber 打满整个 ZBLL 空间),所以这个数对**任何**公式表都一样。两条佐证,都已进 `tests/lsll_class3_structure.test.ts` + `scripts/lsll-class3.mts`:

1. **同一构造在末层上复现社区数字**:216 朝向态 / pre-AUF = **58** 个 OLL(57+跳O),288 置换态 / 两侧 AUF = **22** 个 PLL(21+跳P)。没有人把两步末层定义成「1LLL 的 3916÷4 = 979」;它离 58×22 = 1276 差得远,正如 583,284÷4 = 145,821 离 151,164 差得远。OLL 里同样有对称 case(同公式、不同 AUF 进、不同 PLL 出),社区选的就是乘法。
2. **151,164 恰是商口径的上确界**:对称类取满 494 ⟺ 额外生成元 V ∈ ⟨U⟩,而换公式 = 把 V 在 ZBLL 群内共轭一次。扫完 7776 个元素:**9 个对称类全部够得着**(|Stab|=4 → U^±1,|Stab|=2 → U²)。所以商口径永不超过乘积且够得着;它每低一点,都是某条公式把两个本来不同的 ZBLL case 强行粘掉的信息(当前库粘掉 151,164 − 147,508 = **3,656** 个)。

一处诚实说明:一类、二类数的是**局面**,151,164 数的是**两步路线**。这确实是两种量 —— 但三类问的本来就是路线,而这是它唯一良定义的版本。

### 1.3b mid-AUF 的数学地位(推导细节)

pre 和 post 是状态空间上的**规范**群作用:解条件 g·A·Z·M·B·C = e(A=U^a pre,M=U^m mid,C=U^c post),变 a ⇔ 右乘 U,变 c ⇔ 左乘 U。但**变 m ⇔ g′ = conj_{(BC)⁻¹}(U^k)·g,依赖所选的 phase-2 公式** —— 一个置换只有左右两侧,"第三个 AUF"必然要借助解法的两段拆分才有定义。极端反例:允许 phase-1 直接整个复原(技术上也是"解完槽+EO"),则 mid 商完全退化。

**规范化方式(推荐定义)**:与速拧现实一致 —— 每个 ZBLS case φ 固定一条公式 Z_φ("公式表"),mid 作用定义为 s ↦ s·(Z_φ·U·Z_φ⁻¹)。此时结构非常干净:

- ZBLS 构型空间:槽角 5位×3向 = 15,槽棱 5位×2向 = 10,顶层其余 4 棱 EO = 16,总翻转奇偶约束 ÷2 ⇒ **1,200 个 φ**。
- 商 pre:Burnside 不动点 f(U)=f(U³)=6、f(U²)=12(槽块必须在槽内 + EO 周期化 + 奇偶),(1200+24)/4 = **306**。DB 的 zbls set 恰好 305 个 case = 306 − 1(全解态不算 case)—— 数据与理论闭环 ✓。
- 固定 Z_φ 后,fiber(共享 φ 的 7,776 个态)与 ZBLL 态空间(24·24·27/2 = 7,776)双射;mid = 右乘 U、post = 左乘 U 作用其上,双侧商 = **494 = 通行的 ZBLL 493 + 全解态**(与 DB 闭环 ✓)。
- φ 的 pre-轨道:自由 1,188/4 = 297 类、U²-对称 3 类、全对称 6 类(共 306)。自由类每类贡献 494:

  **商口径 = 297 × 494 + (9 个对称类的贡献) = 146,718 + Δ**,Δ ∈ [502, 4,446]

  9 个对称类的 φ 都是"槽块归位"构型,类内还要再商掉 stabilizer 诱导的作用 —— 这一项就是公式依赖的来源。**Δ 的上端 9 × 494 = 4,446 可达**(§1.3c 的共轭类扫描),于是商口径的上确界 = 146,718 + 4,446 = 151,164 = 306 × 494,与良定义的乘积口径重合。
- **用户的估算 583,284/4 = 145,821 会被略微超过**(不是不足):mid 商在 fiber 上"整除得太狠"的直觉不成立,因为 pre 动的是 φ、mid/post 动的是 fiber 内部,三者不是自由的 (Z₄)³ 积作用。

### 5.1 由此得到的结构(现已实证,非推理)

在"槽统一 FR"的归一化坐标下,**左右镜像和前后镜像给出同一个伙伴 case**:M-镜像∘y′ = S-镜像∘y(因为 S = M∘y²,而 y² 与 M 交换)。即镜像家族不是 4 个 case,而是 **一对 {c, c*}**(自镜像时退化为单个)。"左右/前后/左右+前后"三种镜像的区别体现在**公式(与其所属的 y-view)**层面:

| 公式重写 | 落点 | 字母映射(节选,全表脚本生成并用 KPuzzle 随机态等价性测试验证) |
|---|---|---|
| M(左右镜) | c* 的 FL-view(视图两两对调 FR↔FL、BL↔BR) | R↔L 反向,U/D/F/B 反向,F 仍是 F —— **不产生 B** |
| S(前后镜) | c* 的 BR-view(FR↔BR、FL↔BL) | F↔B 反向,U/D/R/L 反向 —— **F ⇒ B** |
| y²(左右+前后) | **c 自己**的 BL-view(纯旋转,非镜像) | F↔B、R↔L 同向 —— **F ⇒ B** |

锚定检验:`U R U' R'` → M:`U' L' U L`(FL-view)✓ 标准 F2L 镜像;S:`U' R' U R`(BR-view)✓;这与用户"含 F 前后镜像会出 B"完全吻合。F2L 的 A+/A− 命名恰是 {c, c*} 配对;ZBLS 的 ±号子组、自镜像的 F/S/T/O 同构地对上。

### 5.2 F/B 规则 —— **判据已改成看结果(2026-07-26)**

判据只有一条:**生成出来的那条里不许有 B 族**(`B` / `b` / `Bw`)。三份都算一遍,谁带 B 谁出局。

原先按**源公式**的族分三档写:「不含 F 不含 B → 三份;含 F 不含 B → 只生成 M;含 B → 视为该 case 下 B 顺手,三份都给」。最后一档漏了一格:**左右镜保 B 不变**,源里带 B 时它原样带过去,照样生成出要转背面的公式 —— zbls `A+/VP` 就中了这一格(FL 视角落了一条生成的 `y U b' U b U' b' U' b`)。

按结果判还省掉一整段论证。以前得在注释里写清「哪个族经哪次镜像会变成什么」:`S`/`z` 的轴与前后镜的镜面法向平行,轴自己那次翻转与手性那次抵消(`S → S`),冒不出 B;`f` = `F` + `S`,会变 `b`。现在算一遍就知道,不必先证。落到实际分档上,新判据给出的是:

| 源公式 | 能生成的 |
|---|---|
| 不含 F 也不含 B | M、S、y² 三份 |
| 含 F、不含 B | 只有 M(另两份把 F 变成 B) |
| 含 B、不含 F | 只有 S 和 y²(它俩把 B 变回 F;M 保 B) |
| F 和 B 都有 | 一份都没有 |

改判据后重算:f2l 165 → **164**,zbls 181 → **138**,生成条里带 B 的 **0** 条(线上线下同数)。实现在 `mirrorGensFor`,回归见 `tests/alg_mirror_rewrite.test.ts` 的 §5.2 一节 —— 除逐档钉判据外,还有一条拿真语料跑的「凡生成出来的一律不含 B」。

生成条**不过** `validateAlgCase`(原计划要过),理由见 §5.4 ④。

#### 5.3a LSLL 镜像已落地(2026-07-26)

`lib/lsll/mirror.ts` + `tests/lsll_mirror.test.ts`(14 条)。三件当时想当然会踩的:

1. **光用左右镜不行,要再补一个 `y'`** —— M 平面把最后一槽从 FR 送到 FL,单独看出来的不是 LSLL 态;补上 `y'` 把 FL 转回 FR 就对了。这个复合逐面算下来是 `U→U D→D F↔R L↔B`,几何上就是**过 FR 与 BL 两条棱的对角镜面** —— 对角镜面只是这个复合的名字,不是另一个东西。它仍是货真价实的反射:`M y M = y'` ⇒ `(y'M)² = y'(M y' M) = y' y = 1`。
   与 §5.1 是同一件事的两种说法:那边说「M 镜像落到伙伴 case 的 **FL-view**」,把 FL-view 摆回 FR-view 要的正是这个 `y'` 共轭。库里有四个朝向可摆,所以留在 FL-view 讲;LSLL 坐标把槽钉死在 FR,没得摆,只能把 `y'` 吸收进变换本身。
2. **棱的翻向不是原样照搬** —— EO 记法在 F↔R 下不对称(`R` 一枚棱不翻,镜像 `F'` 翻四枚)。逐贴纸推出来是 `eo' = eo + [位置在 E 层] + [块是 E 层块]`;角是 `co' = -co`。判据:`mirrorAlg('R') === "F'"` 且两边末态逐块相等,500 条随机公式对撞。
3. **镜像公式要补 AUF** —— σ(U^a·s·U^b) = U^-a·σ(s)·U^-b,而两个 case 页各自显示各自等价类的 canonical 代表元,AUF 一般对不上。实测:`U2 R U' R'` 的裸镜像 `U2 F' U F` 在镜像 case 页判「没有解掉」。`mirrorAlgForCase()` 试 4 个前置 U 并与开头的 U 合并;往返实测 A+ `U2 R U' R'` ⇄ A− `U F' U F`。

**σ 的不动点 F = 432**(`scripts/lsll-mirror-census.mts` 全量枚举):S 96、O 192、F 144,T **一个都没有**(与 S 只差槽棱翻不翻,却是 0 —— 已显式锁进测试,别当漏算)。大类配对恰好是字母的 ± 对合,S/T/O/F 自映。

### 5.4 同步语义(server 端,`utils/alg_mirror.ts`)—— **✅ 已实现(2026-07-26)**

落地时有四处与原计划不同,都是实现期量出来的,逐条记在下面。代码在
`packages/server/src/utils/alg_mirror.ts`(库层)+ `packages/shared/src/alg_mirror.ts`(纯重写),
行为测试 `tests/alg_mirror_sync.test.ts` 10 条 + `tests/alg_mirror_rewrite.test.ts` 41 条。

**① 整体重算,不做 `mid` 增量。** 原计划给每条原创公式发一个 lineage uuid,编辑时按 `mid` 找同源条覆盖、
删除时按 `mid` 清。实现时改成:**生成条不是状态,是当前原创条的函数** —— 每次改动就把这一对 case 的
生成条全部丢掉重算。省掉的是「三条路径(改 / 删 / 重排)任一漏一次就留孤儿」这个持续风险;
代价是每次编辑多写一行(一对 case 两行),可忽略。`mid` 因此不需要,生成条改带
`gen: 'lr'|'fb'|'y2'` + `src: { id, ori, i }`(源 case id + 视角 + 序号)——
后者比 uuid 更直接:UI 要显示"自动镜像自〈case〉第 N 条"时不用再按 uuid 回查。

**② 只拿第 0 视角(FR)当源。** 四个视角都当源的话,每个视角会被另外三个灌进来,一个 case 的公式数翻两番。
只认 FR 当源,则每个目标视角恰好有唯一来源,**FR 那栏永远是纯人写的**。§5.0 / §5.7 的所有计数本来
也都是按这个口径量的("只数第 0 朝向")。

**③ cls 不参与公式同步**(仍参与建链与 case 页现算)。不是数学问题是数据形状问题:镜像公式落到的是
**别的视角**,而 f2l / zbls 每个 case 存了四个视角数组,**cls 只存一个**(实测 97/97 case 的 `algs` 长度都是 1)。
没有 FL / BL / BR 三个数组,生成的公式没有格子可放。于是名单分两档:`MIRROR_SETS`(f2l/zbls/cls,
有伙伴 + UI 面板)与 `MIRROR_ALG_SYNC_SETS`(f2l/zbls,能写回库)。

**④ 不在 server 端跑 `validateAlgCase`。** 原计划要求生成条过校验才落库。但 server 对**人写的**公式
一条都不校验(POST / PUT 直接落库,校验是 AdminCaseEditor 保存前的事)—— 对机器按固定表重写出来的
公式反而更严一档,说不通。镜像表的正确性改由测试守:贴纸反射 oracle(独立于重写表)+ 两个解析器
对撞 + `mirror-link-plan.mts` 的全库 438/438 + 187/187。

落地后的行为:

- **新增 / 编辑公式**(POST / PUT case):重算这一对 case 的生成条。生成条排在各视角的人写条之后,
  **按源的顺序排**(源第 1 条的左右镜就在目标里排第 1)—— issue 要的"左右镜顺序一致"由此成立。
- **删除 case**(DELETE):`ON DELETE SET NULL` 先把伙伴的链置空,再对**前伙伴**跑一次重算 ——
  它会走"只剥不生成"那条路,正好清掉指向死 case 的孤儿。伙伴 id 必须在删之前问出来。
- **字面重合就跳过**:库里本来就人工收了不少镜像份(f2l `A-` 的 FL 首条 `U' L' U L` 就是 `A+` 首条的
  左右镜、第 2 条 `L F' L' F` 就是 `A+` 第 2 条的左右镜),自镜像 case 更常镜回自己身上一模一样的东西。
- **没建链就静默**:`mirror_case_id` 现在全库是 NULL,所以这套逻辑上线后不产生任何效果,
  等建链脚本跑完才开始生效。这是刻意的 —— 代码可以先上,数据后建。
- 目标 case 不存在时**不自动创建**(2026-07-26 用户拍板:wv/sv/vls 那 243 个新 case 不做,
  而 f2l/zbls/cls 本来就一个不缺,这条分支没有实际输入)。
- **覆盖是有代价的,UI 必须说清楚**:带 `gen` 标记的公式行在编辑器里显式标"自动镜像",并提示改动会在源公式下次编辑时被覆盖 —— 想保留自己的指法请新建一条(新条无 `mid`,不参与同步)。
- **自镜像 case**:落回同 case 的对应 view;字面重合则去重跳过 —— 正是 issue 说的"同一个情况下自动添加多条公式"。
- **范围**:主库 `alg_cases` **与** 社区提交区 `alg_submissions` 都镜像(2026-07-26 拍板)。
- **提交区的镜像条必须带溯源**(用户要求):`gen` + `mid` 之外再存 `srcId`(源提交条 id),**作者仍是原提交人**(不是"系统"),UI 上显式写"自动镜像自 〈case〉第 N 条"并可点回源条。
- **镜像条不计入贡献计数**:提交量 / 排行 / "我贡献了 N 条" 一律只数无 `gen` 标记的原创条,否则提交一条自动变四条,计数虚高四倍。

**⑤ 建链要一个自己的端点**(2026-07-26 补,拿真库跑出来的)。`mirror_case_id` 原本只有读路径:
四个 admin 端点都不收这个字段,而同步只在 case 保存 / 删除时触发 —— 就算 ssh 直接 SQL 把链写进去,
已有公式也不会自己生成。于是加第五个端点 `PUT /:p/:s/mirror-links`,收 `{ links: [{id, mirrorCaseId}] }`,
校验链互指 + id 都在本 set,写完再把整个 set 重算一遍。语义是**全量**:没列在表里的一律解链
(所以"从表里拿掉"就是解链,不用另开接口),`dryRun: true` 只报会改多少不落库。

**⑥ 比对不能逐字 `JSON.stringify`**(2026-07-26 修,只有打真库才暴露)。jsonb 存进去会按(键长, 字节序)
重排键 —— 生成条的 `src: { id, ori, i }` 读回来是 `{ i, id, ori }`,与现构对象逐字不等,于是
「没变就别写」永远判成变了,每次保存白写两行、`updated` 也失去意义。改成排序键后再比。
假库在 `tests/alg_mirror_sync.test.ts` 里补了同款重排(`asJsonb`),去掉修复即变红。
