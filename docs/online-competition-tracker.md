## 1. 目标与建议

已确认：CubeRoot 要能自己办线上比赛，网站和微信小程序都应能承载，后续接入 iOS、Android App；普通魔方和智能魔方都要有，项目应能扩展，至少考虑二、三、四、五阶。当前只规划线上，不加入场馆、陪同人员、现场检录等线下流程。

已确认比赛形式：限定时间内自主参赛与统一时间开赛两种都要支持；先实现限定时间内自主参赛，统一时间开赛放在后续阶段。

已确认首批范围：收费赛事，并开放其他主办方申请办赛；CubeRoot 统一收取报名费，再与主办方结算。支付、退款、主办方申请与权限隔离属于首发范围；平台抽成与结算周期按赛事配置，不设默认值，未配置时禁止正式收费发布；具体数值及申请审核细则仍需定稿。

已确认核验方案：选手在比赛期限内选择监督场次，比赛时实时监督，录像仅用于争议复核。自主参赛指自主选择可用场次，不代表可以在无人监督时随时提交成绩。

实施路线：网站先完成“发布 → 选项目和监督场次 → 报名付款 → 检录候场 → 监督员确认 → 实时监督参赛 → 当场确认成绩 → 公示 → 申诉 → 最终成绩”的完整流程，小程序同期复用赛事浏览和报名页面，再接原生参赛能力；App 沿既有共享架构接入。所有端共用一个赛事与成绩后端。

建议首版普通魔方覆盖二、三、四、五阶；智能魔方先验证三阶及一个明确型号，再按设备能力扩展。不能因系统支持四阶项目就声称支持智能四阶。普通计时与智能首手起表的成绩先分榜，统一起止口径并完成公平性验证后再讨论合榜。

## 6. 比赛规则与参赛流程

### 6.1 维度独立

赛事由“项目 + 设备类别 + 计时口径 + 组别 + 轮次 + 成绩格式”组成。三阶不是智能魔方的同义词；不同计时口径不能无说明合榜。项目 ID 和名称从现有目录映射，不给每个端另建项目表。

首版建议一轮五次取 ao5，二/三/四/五阶普通组各自排名；智能三阶独立排名。轮次数、尝试数、晋级、截止和并列处理属于赛事规则快照。后续增加项目时先验证它的打乱、计时和成绩计算，不能只增加下拉选项。

### 6.2 普通魔方

采用用户已确认方案：比赛期限内自主选择监督场次，现场实时监督与当场确认成绩；不做赛后逐条录像审核。录像仅在争议、申诉或异常复核时使用。监督员由各主办方安排，CubeRoot 可以协助；主办方只能管理本组织赛事的排班，平台协助也须明确落实到授权人员和场次，申请协助不等于排班完成。录像只能提供可复核证据，不能保证杜绝作弊。

选择项目与监督场次 → 同一事务预留报名及场次名额 → CubeRoot 收款 → 支付确认后取得资格 → 场次开放检录 → 检查摄像头/计时环境 → 监督员确认 → 服务端分配正式打乱及尝试编号 → 实时监督打乱、观察、还原并展示成绩 → 监督员当场确认时间/罚时 → 成绩公示。录像保存或补传状态单独显示，不把“全部录像赛后审核完成”作为正常成绩发布条件。

复用键盘/触摸计时与已有外接计时适配；是否允许外部计时器读数手填由比赛规则明确。第一次试赛可由另一设备拍摄，连续画面应能核对本人参赛过程、魔方、打乱/尝试编号与计时结果；单机录制体验作为独立测试项。

证据提交截止可晚于还原截止，但只允许补交原尝试的证据；不能据此重新拧一遍。长视频上传需支持重试与明确失败状态。核验方式若改为实时裁判，则同一报名/尝试/裁决模型保留，增加预约、入场和裁判席。

### 6.3 智能魔方

报名确认 → 支持型号/连接预检 → 领取正式尝试 → 校准状态 → 匹配指定打乱 → 按规则观察 → 首手起表 → 复原停表 → 上报时间、动作流、设备/协议版本、异常记录 → 服务端校验及必要人工复核。

动作流可验证打乱到复原的一致性，但不能单独证明操作者身份或客户端未被篡改。不能宣称智能魔方天然杜绝作弊；录像要求应按赛事风险配置，与普通组同样公布。

正式模式禁用练习中的换题、解法提示、自由修改历史等入口。智能打乱纠偏仅用于到达指定打乱，达到目标后不提供还原指导。

### 6.4 打乱、时间与异常

| 边界 | 建议处理 |
| --- | --- |
| 空项目、错误设备、非法格式、负数/非有限时间 | 发布配置与提交入口校验，返回具体原因 |
| 未报名、未开赛、超过截止、退赛/取消后进入 | 服务端验证资格与时间；前端隐藏按钮不能代替鉴权 |
| 重复领取、刷新、换设备、请求超时 | 同一选手/轮次/尝试返回同一题与状态；一次只能有一个有效执行会话 |
| 异步赛共享打乱泄漏 | D09 必须明确策略；建议首版由服务端给各选手分配独立且固定的随机题，承认题目难度有随机差异；如需同题比较，采用受控同步场次 |
| 正式打乱来源 | 复用现有生成器，但逐项目核验质量/分布并锁定版本；不用已公开的历史打乱，不允许客户端选题或上传自选题 |
| 领题后退出、刷新、蓝牙断线 | 留下尝试和异常，不自动发新题；根据规则续传、待裁判处理或判定无效 |
| 丢步、计时时钟异常、重放提交 | 验证动作序列、会话和尝试身份；客户端签名/哈希不能作为绝对真实性证明 |
| 网络中断 | 本地保留待提交记录并幂等重试；服务端未确认时显示“待提交”，不能显示“成绩有效” |
| +2 / DNF / DNS / 缺次数 / 并列 | 规则快照固定计算与排序；服务端复算，复用已核对的共享算法并补赛事 fixtures |
| 改判与补赛 | 只允许授权裁判按规则操作，保留原值、理由、操作者和版本；补赛关联原尝试 |
| 时间与时区 | 存 UTC 时间与赛事 IANA 时区；清晰展示赛事时区；开赛资格以服务端时间为准，拧动时长用设备/单调时钟 |

服务端掌握正式打乱和结果定稿权。预生成未发布打乱不进入公开 API、静态包、日志或公开缓存；已有联机“按项目共享打乱”代码只复用生成能力，不照搬其可见范围。

赛事状态建议：草稿 → 已发布 → 比赛中 → 公示中 → 已定稿；取消独立。仅争议成绩进入复核，正常成绩不经过赛后逐条录像审核。报名、支付、场次、检录、尝试、证据上传各自拥有状态，不能用一个“已结束”覆盖它们。

已有票种支持多人数量采购；比赛报名必须约束“一赛事一选手一份有效报名、一项目不重复报项”。如以后支持家长代报，付款人与参赛者显式分开；首版不能悄悄把买家等同所有参赛者。收费复用既有交易账本，零元报名也要经过名额和资格事务；迟到回调、超卖、退款后参赛资格必须有确定规则。

外部主办方的订单须能按组织归属核对，结算与退款不能跨组织操作。已确定 CubeRoot 代收后结算；订单收款归平台，主办方查看本组织的收款、退款、平台费用、冻结/可结算金额和结算流水。平台费率及结算周期按赛事条款快照记录，未明确时不开放收费。空值表示未配置，不能隐式当成 0%；明确填写 0% 才表示零抽成。结算周期必须同时包含起算事件与非负整数天数，0 天也须明确填写。主办方编辑配置不等于获准任意修改平台收费协议，正式发布须确认条款版本。自动打款并非已确认需求，首发必须有可执行的对账与结算流程，不能把已收款金额直接视为主办方可提现余额。

### 7.1 接真实接口前的事务约束

- 创建订单同时锁定项目报名和监督场次名额；同账号同项目不得通过购买多张票或切换场次绕过重复报名限制。未支付预留过期与订单取消一起释放。
- 支付回调只有在订单、报名和场次仍可确认时授予资格；迟到回调不得超卖，需进入明确的退款/异常处理流程。
- 换场次必须在同一事务内检查新场次并释放旧场次；不能先释放再抢新名额。退款后的检录/领题资格立即失效。
- 检录仅限本人有效报名，且处于服务端认定的检录时段。前端时钟、查询参数、已登录状态不能单独授予正式尝试权限。
- 监督员需有当前场次指派、不能是该成绩的选手；监督确认记录操作者与时间，失去监督或断线时不能继续领新题。
- 正式 API 必须在收费发布入口校验费用/退款/结算条款与监督员排班，不能仅依赖前端禁用按钮；缺项给出原因。当前仅有本地演示检查，服务端门禁尚未实现。条款在报名后更改必须保留原版本和已报名者处理记录。

公众只读已公开信息；选手读取自己的私有尝试与证据；裁判按赛事授权；管理员操作保留审计。录像使用私有存储、临时访问链接和确定保留期；未成年人资料与公开展示字段在首场前确定，避免默认公开真实姓名或录像。

## 10. 成本、优先级与下次行动

第一版成本重点是监督员排班、实时视频和录像存储。单场录像体积按“选手数 × 人均项目数 × 每项目录像秒数 × 编码码率 ÷ 8”估算（码率为 bit/s）；总存储还取决于保留期内的赛事场数。实时视频测峰值并发和转发带宽；人工成本按监督场次工时及实际争议复核量记录，不按逐条赛后审核估算。参数未定前不报虚构金额或承诺万人同赛。

首版暂缓：平台积分/等级、证书模板商城、复杂赛季、奖金结算、多路实时转播与所有品牌全型号支持；这些属于后续增量，用户确认首发需要时再纳入门槛。收费及开放主办方申请已纳入首版。

真实浏览器已完成本地免费报名（订单 fulfilled、资格 confirmed、余位同步减少）、订单详情（200、已完成、免费、返回比赛）与检录（200、进入赛场等待监督打乱）；原路退款的真实本地数据库回归也已通过。之后的验收重点为双设备摄像监督、实体智能魔方、小程序手机支付和真实支付退款；费用和日期示例不是用户确定的开赛配置，正式收费前仍须在赛事中配置费用、退款与结算条款。

隔离本地 PG 已准备 platform 活动及组织表，并执行本轮迁移和数据库回归；未写生产数据。本文不代表上线或对外办赛已经完成。证据文件默认保留 30 天，未结争议暂缓清理；这属于可配置实现默认值，保留政策仍需在正式参赛规则中明确。

### 支付、退款与结算的当前实现证据（2026-09-10）

- 微信小程序复用既有登录与微信支付栈：赛事网页订单跳转原生支付页，通过本人账号绑定校验后创建 JSAPI 支付参数，调用 `requestPayment`；取消可重试，回站及前台轮询均以服务器订单状态确认到账。返回原网页不携带登录令牌，抖音或不支持的运行环境显示准确提示。相关路径为 `apps/miniprogram/src/pages/payment/`、`apps/api/src/platform/payment.ts`、`apps/api/src/payment/wechat.ts`（相对 `core/`）。
- 线上赛事订单已接入“本人申请 → CubeRoot 管理员批准 → 原渠道全额退款 → 成功后撤销资格及调整结算”。微信、支付宝复用既有签名与商户配置；Airwallex 适配器支持其真实退款 API，但当前平台赛事下单未提供 Airwallex 选项。`0228_platform_provider_refunds.sql` 持久保存批准与唯一渠道请求号，后台定时对账、超时或重复操作复用同一请求，未确认成功不会撤销参赛资格。既有人工凭证登记仅用于外部已完成退款；已有批准的自动退款禁止再走人工登记，避免重复退款。本轮没有调用真实资金接口。
- `0226_competition_settlement_ledger.sql` 增加结算台账。读取实际已收款与成功退款，按赛事已配置费率计算应结算金额；只有 CubeRoot 管理员能登记已完成的外部转账，金额必须等于当前差额，并校验定稿、结算等待期、未结争议与待退款。每笔保留结算快照及审计、去重转账凭据，后续退款追加调整记录，负差额须登记实际追回款项后对平。接口只记账，不自动打款或假定主办方已经收款。
- 验证：小程序 `check:all` 通过 31 个测试文件、316 项测试，并完成微信构建与抖音转换构建；Web bridge 9 项及微信 RSA 签名/响应验签 7 项通过；API typecheck、文档 schema/API drift 6 项通过。独立本地 PostgreSQL 实际执行 0226，2 项集成回归验证取整抽成、待退款/争议阻挡、历史转账快照不变、退款调整不重复及追回后差额归零。首跑因本机负载使建库 hook 超时，30 秒 hook 重跑通过，未放宽金额断言。
- 自动退款补充验证：18 项路由/渠道契约测试、9 项微信签名与支付退款传输测试、1 项真实 PostgreSQL 0228 迁移/状态守卫测试通过；真实 PG 覆盖旧记录保留、请求号唯一且不可变、批准后失败重查、成功终态不可倒退。审查修复 bigint 本人权限比较、NaN 金额漏验与退款 JSONB 元数据双编码。外部资金 API 均使用 mock，未把契约测试当作渠道到账证明。
- 完整履约追加验证：`competition_refunds_pg.test.ts` 使用隔离本地 PostgreSQL，实际执行 0142/0167/0224/0226/0228 迁移，保留真实订单、事务、状态守卫和履约代码，仅替换身份及渠道 I/O。2 项 PG 回归与 7 项退款路由回归共 9 项通过：收费订单创建、支付尝试与已验证通知授予资格；本人申请、管理员批准后处理中仍保留资格；渠道成功后订单/支付/报名均退款、释放名额、轮换视频授权、履约逆向记录和退款后结算调整各一次；重复对账与支付通知不重复执行。夹具预置一笔历史外部转账，退款后正确形成待追回差额，不代表实际银行转账验收。另一项验证未付报名到期取消、名额释放、支付尝试取消及过期任务重放幂等。真实运行暴露并修复支付通知及过期任务 JSONB 双编码、退款状态参数的 text/varchar 推断冲突；上述失败未被放宽断言掩盖。外部资金仍未调用。
- 未实测：微信真机支付、支付渠道真实退款、外部银行转账/追回、小程序开发者工具关闭重开后的干净编译、正式域名及业务域名发布验收。本轮没有扣款、退款、打款或发布小程序；启用真实微信小程序支付仍依赖正确的 AppID/商户 JSAPI 配置与明确的 `WECHAT_MINI_PAY_ENABLED` 开关。自动退款也要求原支付商户的有效凭据及响应验签配置；缺配置或不匹配商户时明确拒绝批准执行。iOS/Android 原生宿主的赛事支付验收不包含在上述小程序构建证据中。
