# CubeRoot 线上赛事规划与跟踪

状态：`DRAFT / NOT IMPLEMENTED`。创建日期：2026-09-10。

本轮交付为规划与跟踪文档；未授权启动业务实现。已确认目标、建议方案、待确认决策和实现证据分别记录，未答复的建议不视为用户决定。

## 1. 目标与建议

已确认：CubeRoot 要能自己办线上比赛，网站和微信小程序都应能承载，后续接入 iOS、Android App；普通魔方和智能魔方都要有，项目应能扩展，至少考虑二、三、四、五阶。当前只规划线上，不加入场馆、陪同人员、现场检录等线下流程。

建议路线：网站先完成“发布 → 报名 → 参赛 → 审核 → 公示 → 申诉 → 最终成绩”的完整流程，小程序同期复用赛事浏览和报名页面，再接原生参赛能力；App 沿既有共享架构接入。所有端共用一个赛事与成绩后端。

建议首版普通魔方覆盖二、三、四、五阶；智能魔方先验证三阶及一个明确型号，再按设备能力扩展。不能因系统支持四阶项目就声称支持智能四阶。普通计时与智能首手起表的成绩先分榜，统一起止口径并完成公平性验证后再讨论合榜。

| 面向对象 | 第一版页面/能力 |
| --- | --- |
| 访客 | 赛事列表、赛事详情、规则、日程、允许公开的选手名单、已发布成绩 |
| 选手 | 选择参赛项目、确认规则、报名状态、赛前设备检查、正式参赛、证据上传进度、个人结果与申诉 |
| 管理员 | 建赛、配置项目/组别/轮次、发布、报名管理、异常处理、成绩审核、公示及定稿 |
| 裁判 | 仅查看所分配赛事的证据、提出改判与理由；本人参赛成绩交其他裁判审核 |

## 6. 比赛规则与参赛流程

### 6.1 维度独立

赛事由“项目 + 设备类别 + 计时口径 + 组别 + 轮次 + 成绩格式”组成。三阶不是智能魔方的同义词；不同计时口径不能无说明合榜。项目 ID 和名称从现有目录映射，不给每个端另建项目表。

首版建议一轮五次取 ao5，二/三/四/五阶普通组各自排名；智能三阶独立排名。轮次数、尝试数、晋级、截止和并列处理属于赛事规则快照。后续增加项目时先验证它的打乱、计时和成绩计算，不能只增加下拉选项。

### 6.2 普通魔方

报名确认 → 查看规则并测试计时/录像 → 在参赛窗口领取正式尝试 → 显示服务端打乱及尝试编号 → 连续录像中打乱、观察、还原并展示成绩 → 提交时间/罚时和录像 → 裁判核验 → 成绩公示。

复用键盘/触摸计时与已有外接计时适配；是否允许外部计时器读数手填由比赛规则明确。第一次试赛可由另一设备拍摄，连续画面应能核对本人参赛过程、魔方、打乱/尝试编号与计时结果；单机录制体验作为独立测试项。

证据提交截止可晚于还原截止，但只允许补交原尝试的证据；不能据此重新拧一遍。长视频上传需支持重试与明确失败状态。核验方式若改为实时裁判，则同一报名/尝试/裁决模型保留，增加预约、入场和裁判席。

### 6.3 智能魔方

报名确认 → 支持型号/连接预检 → 领取正式尝试 → 校准状态 → 匹配指定打乱 → 按规则观察 → 首手起表 → 复原停表 → 上报时间、动作流、设备/协议版本、异常记录 → 服务端校验及必要人工复核。

动作流可验证打乱到复原的一致性，但不能单独证明操作者身份或客户端未被篡改。不能宣称智能魔方天然杜绝作弊；录像要求应按赛事风险配置，与普通组同样公布。

正式模式禁用练习中的换题、解法提示、自由修改历史等入口。智能打乱纠偏仅用于到达指定打乱，达到目标后不提供还原指导。

### 6.4 打乱、时间与异常

| 边界 | 建议处理 |
| --- | --- |
| 空项目、错误设备、非法格式、负数/非有限时间 | 发布配置与提交入口校验，返回具体原因 |
| 未报名、未开赛、超过截止、退赛/取消后进入 | 服务端验证资格与时间；前端隐藏按钮不能代替鉴权 |
| 重复领取、刷新、换设备、请求超时 | 同一选手/轮次/尝试返回同一题与状态；一次只能有一个有效执行会话 |
| 异步赛共享打乱泄漏 | D09 必须明确策略；建议首版由服务端给各选手分配独立且固定的随机题，承认题目难度有随机差异；如需同题比较，采用受控同步场次 |
| 正式打乱来源 | 复用现有生成器，但逐项目核验质量/分布并锁定版本；不用已公开的历史打乱，不允许客户端选题或上传自选题 |
| 领题后退出、刷新、蓝牙断线 | 留下尝试和异常，不自动发新题；根据规则续传、待裁判处理或判定无效 |
| 丢步、计时时钟异常、重放提交 | 验证动作序列、会话和尝试身份；客户端签名/哈希不能作为绝对真实性证明 |
| 网络中断 | 本地保留待提交记录并幂等重试；服务端未确认时显示“待提交”，不能显示“成绩有效” |
| +2 / DNF / DNS / 缺次数 / 并列 | 规则快照固定计算与排序；服务端复算，复用已核对的共享算法并补赛事 fixtures |
| 改判与补赛 | 只允许授权裁判按规则操作，保留原值、理由、操作者和版本；补赛关联原尝试 |
| 时间与时区 | 存 UTC 时间与赛事 IANA 时区；清晰展示赛事时区；开赛资格以服务端时间为准，拧动时长用设备/单调时钟 |

服务端掌握正式打乱和结果定稿权。预生成未发布打乱不进入公开 API、静态包、日志或公开缓存；已有联机“按项目共享打乱”代码只复用生成能力，不照搬其可见范围。

## 7. 后端数据边界

下列为概念模型，不是已批准的迁移；最终表名和复用关系在 M1 定稿。

| 对象 | 核心内容 |
| --- | --- |
| 赛事竞赛配置 | 关联 platform 活动、主办方、线上形式、报名/参赛/补证/申诉时段、规则版本 |
| 参赛项目/组别 | 现有项目 ID、普通/智能、计时口径、设备允许范围、名额与成绩格式 |
| 选手报名与报项 | 一个账号对应明确参赛者、所选项目、资格、状态，关联既有活动报名/订单 |
| 轮次 | 开始/结束、尝试数、晋级规则、赛制快照、状态 |
| 正式尝试与打乱分配 | 选手/轮次/序号唯一、服务端分配、开始凭证、原始时间/罚时、接收状态、异常 |
| 证据与裁决 | 私有录像引用、智能动作记录、审核状态、改判原因、申诉与裁决记录 |
| 成绩发布版本 | 服务端复算结果、临时/最终标记、发布时间、更正版本 |

赛事状态建议：草稿 → 已发布 → 比赛中 → 审核中 → 公示中 → 已定稿；取消独立。报名、支付、尝试、证据上传各自拥有状态，不能用一个“已结束”覆盖它们。

已有票种支持多人数量采购；比赛报名必须约束“一赛事一选手一份有效报名、一项目不重复报项”。如以后支持家长代报，付款人与参赛者显式分开；首版不能悄悄把买家等同所有参赛者。收费复用既有交易账本，零元报名也要经过名额和资格事务；迟到回调、超卖、退款后参赛资格必须有确定规则。

公众只读已公开信息；选手读取自己的私有尝试与证据；裁判按赛事授权；管理员操作保留审计。录像使用私有存储、临时访问链接和确定保留期；未成年人资料与公开展示字段在首场前确定，避免默认公开真实姓名或录像。

## 8. 各端交付

| 端 | 建议首阶段 | 完整参赛阶段与验收 |
| --- | --- | --- |
| 网站 | 全部管理与参赛主流程；普通四个项目、受验证的智能三阶 | 桌面与窄屏、刷新/断网恢复、真实上传、正式成绩流程 |
| 微信小程序 | 通过现有 web-view 复用列表、详情、报名、我的比赛、结果 | 原生计时/BLE 接入比赛会话；iOS/Android 微信分别做真机验证 |
| Android App | 按现有工具/账号在线 surface 展示赛事内容 | 共享计时器接正式尝试，原生 BLE/文件能力实测 |
| iOS App | 与 Android 同一 App 产品层和 API | iPhone 上连接、后台中断、文件上传与正式参赛实测 |

网站能显示小屏页面不意味着所有手机浏览器都能连接智能魔方。已查 [Chrome 官方说明](https://support.google.com/chrome/answer/6362090?co=GENIE.Platform%3DiOS&hl=en)：iPhone/iPad 的 Chrome 不支持网站连接蓝牙设备。因此智能赛不能只交付网页就声称覆盖 iPhone；小程序原生 BLE 与 App 原生 transport 是要单独完成的路径。

微信 web-view/BLE 官方页面本轮未能获取；现有小程序源码只作为仓库实现依据，具体基础库、桥接、权限及手机行为在 M0/M4 重新核验。桌面小程序可点选不替代手机连接验收。

保持 `docs/cross-platform-app-contract.md` 的分层：Next 页面留在 client；共享规则、模型、计时和协议走已有 shared/timer-ui；安装端产品组合走 app-ui；原生 API 留宿主；小程序保留必要的 WXML/平台适配。网站与小程序不共享 React DOM 源码。App 发布状态仍只在 `docs/mobile-app-roadmap.md` 记账，本文件仅跟踪赛事接入依赖，不复制五端总体完成勾选。

## 10. 成本、优先级与下次行动

第一版成本重点是裁判审核和录像上传。单场录像体积按“选手数 × 人均项目数 × 每项目录像秒数 × 编码码率 ÷ 8”估算（码率为 bit/s）；总存储还取决于保留期内的赛事场数，审核成本取决于录像总时长和复核比例。实时视频另外测峰值并发和转发带宽。参数未定前不报虚构金额或承诺万人同赛。

首版暂缓：平台积分/等级、证书模板商城、复杂赛季、奖金结算、开放主办方入驻、多路实时转播与所有品牌全型号支持；这些属于后续增量，用户确认首发需要时再纳入门槛。

下一步先收敛已提出的赛制、核验、收费及办赛主体问题，将首场比赛写成一份可直接配置的样例，然后定稿 M1。本文不代表实现、上线或对外办赛已经完成。
