更新：2026-10-15。状态：**报告内容、显示规则与交互状态已改为同一源码；新版已安装，完整真机交互验收进行中**。以下历史补证保留各次验证边界，最新状态以本节为准。

## 同一源码的报告契约（本轮交付）

- `timer-ui/reconstruct/report-content.ts` 统一摘要、日期、报告区块顺序、显隐、分步表、参考、原始动作、反馈、分享及折叠状态；`report-notation.ts` 统一还原步骤、化简、行内注释、颜色、案例与动作定位。
- `report-player.ts` 统一播放/暂停、重播、前后一步、定位、倍速与陀螺仪切换，以及逐步动画时长。Web/iOS 原组件与 Watch 均调用这些函数，不保留一份 Swift 业务规则副本。
- `ReportContent.tsx` 是 React 绘制器，Watch 的 `WatchReportNodeView` 是原生绘制器。Swift 只处理通用节点、小屏换行/横向滚动、系统分享、生命周期、三维场景与触摸输入；报告项目、文案、条件及动作由共享节点给出。
- 当前共用速度为 0.5×/1×/2×，以现有 React 控件为准。原始动作表仍只显示数据；可定位的还原步骤通过共享边界映射播放，不能给原始动作表另加源平台没有的交互。
- 后续修改这些共享文件的内容、规则或动作，重新构建并安装 Watch 就会带入；并非在线热更新。新增平台能力或一种全新绘制节点时，仍需补对应宿主适配。离线公式库的更新继续按既有快照刷新入口执行。
- 分析缓存指纹覆盖分析依赖、缓存结构、手表求解预算与离线数据；仅报告样式/展示改动不再使分析缓存失效。报告树仅在内容/状态变化时传给 Swift，折叠区不传隐藏子节点，化简结果不随播放帧重复计算。

本轮验证：app-ui 类型检查通过，报告/排版/共享契约 47 项和原生播放器 2 项通过，真机及模拟器构建、签名校验通过。四把真实记录在实际 32 MiB QuickJS 宿主分别得到 65/69/56/64 STM、七段，均完成且无错误；这些是 Mac 执行结果，不代表手表耗时。

新版已覆盖安装 Series 8（安装回执序号 1100）。直接读取新版真机日志得到 `sharedReport=true`，区块为 summary/actions/playback/analysis/references/raw，11.524 秒记录为 64 STM、5.553627 TPS、七段；`analysisPending=false`、错误为空。冷分析引擎 CPU 为 5265.333 ms，不等于用户墙钟等待时长。缓存重开与手动播放交互尚待本轮补证，不沿用旧版验收冒充。

随后修正用户截图中的原生行内对齐：`WatchReportFlow` 原先按各子项顶部定位，10 点高的色块高于文字；现在按每行实际高度垂直居中，不更改共享内容或颜色规则。41mm 模拟器已看到对齐后的注释，并实际播放到 69/69，最终六面各自同色，无分析错误。补丁真机/模拟器构建与签名通过，覆盖安装回执序号 1108；远程启动报告设备锁定，最终手表屏幕确认仍待用户解锁。

## 共同事实源

基准为 `timer-ui/src/reconstruct/ReconstructReport.tsx`，Web 和 iOS/Android
共同使用。微信/抖音的计时复盘通过该网页报告消费。Watch 只保留 QuickJS 调度、

## 方法自动识别（替代此前审计建议）

维护者明确要求不显示「还原方法」选择器，不能只隐藏选择器而固定方法。
已从 React 报告和 Watch 删除入口，统一调用 shared 的 `detectSolveMethod`。
已有平台原先只有方法内的分段、朝向和案例检测，没有完整方法分类；这次增加的分类
是在共享层复用这些现有阶段谓词，不能声称原来已有跨方法分类。

- 自动根据完成记录的阶段顺序选择 CFOP、Roux 或 ZZ；ZBLS/ZBLL 继续由 CFOP 的案例识别处理。
- CFOP 先复用既有十字朝向归一化，Roux/ZZ 按完整两块完成情况选同一观察框架，
  防止打乱中偶然已有的一块锁死错误朝向。允许 Roux 的 CMLL 跳步。
- EOcross、过短/未完成或可由多种方法产生的同一序列无法唯一反推人的意图，保留 CFOP。
  尚无 Petrus 等方法的现有阶段契约，不声称支持所有还原法。
- 分类只依赖动作顺序，不因实时计时数字更新重跑完整候选搜索。

## 性能与卡住根因

1. OLL/PLL 索引原先每次冷建；改为构建时运行原 builder，手表加载其序列化结果。
2. QuickJS 将私有字段降级为 WeakMap 导致内存膨胀；使用其支持的原生私有字段。
3. 公式匹配先用既有指纹缩小候选，并在候选/阶段间让出执行；完整状态等价校验保留。
4. 两个消费者请求同一离线公式集时，旧 Map 会覆盖其中一个 resolver；现在共用同一 Promise。
5. 原 worker 的 60 秒墙钟超时把 watchOS 挂起算作分析时间：真机出现约 64.9 秒后
   `Analysis failed`。Watch 的 timer adapter 改用每次 QuickJS 执行累计的线程 CPU 时间；
   跨队列线程迁移不比较不同线程的时钟。成绩和播放继续使用原有真实时间。
6. 分析随整个复盘页调度，不依赖三维视图是否滚出屏幕；进入后台可以暂停，亮屏继续。

`analysisMs` 在这版手表日志中表示引擎 CPU 耗时，**不是用户等待时长**。
独立本机 QuickJS 32 MiB 运行 13.983 秒记录约 1.6 秒 CPU，不能冒充 Series 8 实际耗时。
参考求解原先在本机诊断中超过 96 MiB；Watch 保留 32 MiB 运行时与逐次执行 CPU 保护，
以宿主预算限制原求解器，不为追求参考项齐全取消保护。未得到参考不影响分段和回放。
