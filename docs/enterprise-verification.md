# 企业对公账户认证

本功能在现有企业工作区中独立管理认证，不改变组织成员、公开培训机构目录、学生归属或品牌授权。创建组织不等于认证通过；企业认证也不证明品牌或商标权利。

## 入口和状态

- 企业所有者/管理员：`/zh/org/{slug}` 概览底部「企业认证」。普通成员不开放材料和申请操作。
- 平台管理员：`/zh/org` 的「企业认证审核与收款设置」。管理入口使用有身份的管理员会话，不接受匿名管理员 API key。
- 申请流程：填写主体与经办人资料、营业执照和付款对公账号 → 获取金额及附言 → 企业自行向指定账户转账 → 申报已打款 → 平台复核 → 通过或拒绝。
- 状态：`awaiting_transfer`、`pending_review`、`verified`、`rejected`、`expired`、`revoked`。
- 转账窗口为 7 天，金额 0.01–0.99 元，以分存储。附言是每申请独立的 18 位 ASCII 字符串。金额不能单独用于认领款项。
- 未申报的申请到期后禁止提交；已申报申请可继续审核，但用于认证的银行到账时间必须在原申请窗口内。

## 生产启用前的配置

维护者已选择使用现有招商银行对公账户。本地代码不包含真实收款账号、支行、密钥或生产测试款。

1. 按仓库发布流程部署 API 与 migration `0271_enterprise_verification`，并通过 `deploy_nginx.yml` 发布认证接口的 3 MiB 请求限制（兼容 Base64 执照）和关闭临时盘缓冲的配置；本地修改不等于线上已启用。
2. 在 API 运行环境配置 `ENTERPRISE_VERIFICATION_KEY`：独立的 32 字节随机 AES 密钥，Base64 编码。使用已有密钥管理与备份渠道，禁止提交。系统不会自动生成后丢弃密钥；更换密钥必须先完成存量数据重加密，不能直接覆盖旧密钥。
3. 平台管理员在上述入口填写真实企业户名、招商银行开户支行、对公账号和明确的退款时限说明，再开启申请。只有密钥和收款信息就绪才接收申请。
4. 收款信息保存为每申请的加密快照。后续更换收款账户只影响新申请；暂停申请也不撤销已发出的转账指引，必须继续监测旧收款账户。
5. 真实上线验收需用企业自己的对公账户完成一笔真实小额转账，从银行核对到账、审核并实际退款。当前本地数据库和页面 fixture 验证不构成银行实款验收。

## 审核和资金核对

本期采用人工查银行流水，未接入招商银行银企直联、自动对账或自动退款。程序不会发起真实转账。

- 核对工商登记的企业全称、统一社会信用代码、法定代表人、经营状态，并比对营业执照。信用代码格式和校验位只过滤录入错误，不是工商真实性认证。编码规则参考 [GB 32100-2015](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=24691C25985C1073D3A7C85629378AC0)。
- 核实经办人的企业授权，在审核说明中记录查询来源和授权依据。声明开关、执照图片或打款截图本身不能替代核验。
- 从银行后台/对账单登记真实的流水号、付款户名、完整付款账号、金额、附言、到账时间。不得照抄申请预期值冒充实际流水。银行流水与收款账号组合全局唯一，不能复用同一笔款认证多个企业。
- 认证通过要求付款户名等于企业全称、付款账号等于申报对公账号，金额/附言准确匹配，到账时间在有效期内，且三项材料/授权核验都完成。经办人和该机构的活跃成员不能审批自己的机构。
- 同一信用代码最多有一个有效认证；已有企业需要认领时由平台处理，不能靠创建同名组织获取既有学生或企业权限。
- 实际已到账但金额、户名、账号或附言不符，以及逾期款，可以单独登记到账并退款，不能因此通过认证。每申请登记一笔银行款，重复误付等需财务另外追踪；不能覆盖已有流水。
- 退款先通过银行退回「实际到账记录中的原付款账户」，再登记退款流水号。登记动作只形成审计记录，不执行退款。审核拒绝和撤销认证不删除银行流水或退款记录。
- 审核员发现登记错误时暂停审核，交由受控数据更正流程处理；前台不能直接改写原始流水，避免悄悄改变已经作出的审核依据。

## 数据边界

- 营业执照仅允许 JPEG/PNG、最多 2 MiB，校验 Base64 和文件签名；不支持 SVG、HTML 或公开文件 URL。
- 材料、联系人、完整银行账号和银行流水详情采用已有 AES-256-GCM 封装加密，AAD 绑定申请 ID；收款设置使用独立 AAD。企业名、信用代码、认证状态和时间用于约束及查询。
- 所有认证接口 `Cache-Control: no-store`，材料只能由已登录的平台管理员按申请读取，访问有审计记录；列表不返回证照和付款账号。
- 服务端不输出 SQL 参数、解密材料或账号到日志。查看材料、申请、申报、审核、到账、退款和撤销均保留操作者及时间。
- 材料保留期限和到期清理应在正式开放前纳入平台隐私与留存政策；本实现不自动删除仍需对账或审计的材料。

## 验证

本地专用 PostgreSQL socket 下的独立随机 schema 覆盖：migration、跨机构越权、未配置拒绝受理、并发幂等申请、收款快照、加密、未到账不认证、自审拒绝、付款不匹配、重复信用代码/流水、退款幂等、撤销及过期异常款退回。

在本机临时 PG 位于 `/tmp/cuberoot-institution-pg`、端口 `54329` 且已启动时，可在 `core/` 运行：

```sh
ENTERPRISE_PG_TEST=1 pnpm --filter @cuberoot/server exec vitest run tests/enterprise-verification.test.ts tests/enterprise-verification-pg.test.ts
```

测试仅使用固定假资料和随机 schema，结束删除 schema；不会连接生产库或操作真实银行账户。常规 CI 未配置该临时 PG 时跳过 PG 集成用例，纯规则用例正常运行。
