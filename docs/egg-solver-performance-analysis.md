# egg 为什么更快：Opt10 复盘与本机、阿里云 Opt8 实测

2026-11-09，PST。前九节为此前 Opt10 源码和已有记录的分析；末尾新增用户随后授权的本机、阿里云 h8 实测，不能把两个阶段混为同一次实验。相关任务状态见 [Timer 跟踪文档](timer-optimal-egg-tracker.md)。本次复查没有调用 Agent。

**最新结果（2026-11-11，PST）：阿里云瓶颈已找到并有对照证据。egg 的 x86 大表预取使用 NTA，在这台 Intel Skylake 云机上代价很大；改为 T0 后，正式源码版 100 题用 36.392 秒，同轮 Opt8 为 72.907 秒，速度约 2.00 倍。** 全部 200 个解独立回放正确、最优步数一致，CPU、慢题和空闲检查全部通过。定位方法和限制见第十一节；Timer 上线状态按[跟踪文档](timer-optimal-egg-tracker.md)记录。本机 M5 Max 的 3.44 倍与原云端失败记录均保留，不能把它们改写成同一轮结果。

**核心判断：egg 的优势来自整套搜索执行方式的配合——滚动交错查表、较低的每节点处理成本、更充分的查询复用，以及跨线程工作共享。少查表只能解释一部分；仅增加 lanes、增加剪枝或开启编译选项，不能自动获得同样收益。** 本机同容量比较约快 2.10 倍已有实测支持，但还没有本机逐项开关实验，不能给每个优化分配一个确定贡献百分比。

**一、先把“快两倍”的比较对象说清楚**

同一台 M5 Max / 128 GiB，同一组 WCA1000，16 个搜索线程、一次处理一个魔方，每引擎一轮、无预热。比较的是求解时间之和，不含加载、完整性扫描和外部验解。两边都是原生 Rust / NEON，并非拿原生程序和浏览器解释执行相比。

| 项目 | 我们冻结的正式 Opt10 | egg h10 |
| --- | ---: | ---: |
| 主表数据 | 31,130,910,720 字节 | 31,130,910,720 字节 |
| 1000 题求解总时间 | 22.685558 秒 | 10.804456 秒 |
| 每题时间中位数 | 13.296 ms | 6.176 ms |
| 每题 P95 | 98.293 ms | 46.575 ms |
| 逻辑主表查询 | 6,357,661,822 次 | 5,618,135,198 次 |
| 每线程交错搜索数量 | 8 contexts，分阶段推进 | 32 lanes，滚动推进 |

时间减少 **52.37%**，速度为 **2.09965 倍**。按题号重新匹配已有原始输出，egg 在 **973/1000 题**更快，逐题速度比的中位数为 **2.1197**。不能把总体优势理解成每一题都更快。

两张表容量相同，但索引定义与内容不同，并非同一个文件；两套引擎也没有相同搜索顺序。查询量差包含下界、查询复用、访问顺序和并行结束时机等影响，不能全部归给某一条剪枝或缓存规则。

| 17 步 | 266 | 1.332548 秒 | 0.609585 秒 | 2.19 倍 |
| 18 步 | 656 | 16.154238 秒 | 7.725629 秒 | 2.09 倍 |

18、19 步题占了我们约 94% 的求解时间，优势同样存在。因此不能仅用“简单题省掉线程启动”解释全局结果。这仍是一轮观察，不能据此声称重复运行、其他硬件、所有题目都固定快 2.1 倍。

上游 README 的 **20.3 倍**另有条件：48 核 EPYC、1 GiB 大页、其指定的 cube48opt10 竞争版本和测试集。上游把 `cube48opt10` 与我们仓库的 `cube48opt-rust` 分开列出，不能因名称相近，把那一行当成对我们当前正式 Opt10 的本机测量。[上游比较说明](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/docs/comparisons/README.md)

**二、数据直接说明：重点不只是少搜索**

egg 的大表查询减少 **11.63%**。如果每次查询连同周围计算的平均成本完全不变，这只对应约 **1.132 倍**速度，不足以解释 2.10 倍。

把现有总量作算术分解：

`2.09965 = 查询次数比 1.13163 × 全程平均每次逻辑查询成本比 1.85542`

后一个数字含坐标计算、状态变换、剪枝判断、线程启动、调度、等待等全部时间，**不是内存访问本身快了 85.5%，也不是某个优化的独立贡献**。它提示我们应该重点研究“怎样执行这些工作”，而不是只看又少了多少搜索节点。

两边节点计数定义不同：egg 会计入一些已经跳过、没有实际生成的等价兄弟节点，不能直接拿节点总量比算法优劣。逻辑查询数也不是物理内存读取数或缓存未命中数。相关数字已从旧 JSONL 重新汇总，没有运行求解器。

**三、最重要的实现差异：让查表和计算持续交错**

这个表不是保存所有完整解答的字典，而是给搜索提供“至少还需要几步”的下界。程序反复计算索引、查下界、判断能否排除一条搜索路线。几十 GB 的表远大于 CPU 缓存，随机查表时会遇到等待。

我们的旧实现已经做了交错和预取，不能描述成“我们每次都傻等”。实测 Opt10 每线程维护 8 个上下文，循环大致是：先为一批上下文计算逆侧地址，再读取逆侧并为存活者准备正侧地址，再读取正侧，随后集中处理回退、分裂和下一步。

egg 把每条 lane 做成可暂停的搜索状态机：到某条 lane 时，取上次已预取的结果，继续计算到下一次需要查表，发出预取后立即换另一条。每条 lane 有自己的进度，不要求所有 lane 一起进入同一阶段。下一轮回到它时，其他 lane 的计算为这次内存读取提供了等待间隔。

区别因此是 **推进顺序、预取间隔、每轮管理成本和可用并行工作共同变化**，不是简单把 8 改成 32。32 lanes 也不是 32 个系统线程，不保证硬件同时存在 32 个 DRAM 请求。

上游历史记录支持这条方向：从其递归版本改成 lane 搜索，48 线程吞吐从 276.9 到 434.7 题/秒；之后从三阶段推进改成滚动推进，从 491.7 到 570.1 题/秒。前一个改动同时改变了查询量，后一个同时改变了 lane 数，均不是只隔离一个因素的本机实验，不能把约 57% 和 16%直接套在我们机器上。

源码：egg [`src/lanes.rs`](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/src/lanes.rs) 的模块说明和 `advance`；我们冻结源码 `src/search.rs:932`、`:1032`、`:1128`。上游原始记录：[lane 搜索](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/docs/history/commits/2bb148d5026e.md)、[滚动调度](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/docs/history/commits/5cea944d0141.md)。

**四、让每次搜索少做无用工作**

1. **延后计算很可能用不到的另一侧状态。** 我们的冻结版 `Frame::child_counted` 先调用 `moved_pair` 生成正、逆两侧状态；之后若第一侧查询失败，另一侧状态的生成就白做了。egg 对常见四分之一转先只算首先要查的那一侧，第一侧通过后才算另一侧。我们已经会在第一侧失败时跳过第二次主表查询，因此这里新增的差异主要是更早的状态构造和存储，不是从“两次都查”变成“只查一次”。

2. **同面正反四分之一转复用成功查询。** 对这个特定半转子群下界，某一侧的 `F` 与 `F'` 孩子可以共享下界。我们正式版已有“一个失败就剪掉等价兄弟”的规则；egg 还把成功值保存下来，轮到对应兄弟时直接用。我们以前也试过成功缓存，但当时整体更慢，所以冻结 Opt10 没启用 `quarter-cache`。不能说我们没发现这个数学关系。

3. **便宜的角块信息先排除，必要时加强压缩后的下界。** egg 在本来就要做的坐标归类中取到角块下界；若它已证明步数不够，省去大表查询。主表压缩码为 0 时还取块内最小值与角块下界的较大者。我们冻结 Opt10 的 `prepare` 返回主表索引，没有这条角块提前拒绝路径。这不是额外加载一个巨大角块表，也没有证据说它单独贡献了大部分提速。

4. **缩短最频繁执行的代码。** egg 用动作掩码一次跳过无效兄弟，按实际角色保存两侧状态，尽量少反复读写栈字段，把少见路径移开；x86 上还采用位提取、SIMD 选择和针对性的代码布局。小改动重复几十亿次可能有价值，但具体收益依赖编译器、CPU 和其余代码。

双方都有 NEON、预取、release、fat LTO 和单 codegen unit。把本机差距归因于“对方用了 SIMD/编译优化，我们没用”不符合事实。上游 AVX-512、BMI2、Linux 大页的成绩也不能直接解释这次 ARM Mac 的差距。

这类优化有配合关系：上游的延后状态计算旧尝试也失败过；后来把动作选择改为查掩码、减少待存状态、调整寄存器生存期等一起修改，才得到新结果。其五项组合在某次布局平均测试中约提升 1.5% 单线程吞吐，48 线程基本持平。**同一个优化名称，可能对应完全不同的机器指令和额外成本。** [该组原始实验](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/docs/history/commits/f8a4919d0675.md)

源码定位：我们冻结版 `src/search.rs:274`、`src/opt10.rs:75` 和 `coset-build.json`；egg `src/lanes.rs:1442`、`:1487`、`:1585`，以及 `src/solver.rs:201`、`:225`。查询复用的上游历史记录为 [twin lookup](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/docs/history/commits/0b65adffa572.md)：当时其查询约少 29%、吞吐约增 10%，基线不同，不是本机贡献分解。

**五、并行不是开足线程就结束：还要处理空等与尾部任务**

我们的冻结 Opt10 已有动态前缀领取和线程内部的上下文拆分，不是完全静态分工。但是每个新魔方会创建一组 scoped workers；在一题内部，各深度之间通过命令通道和结果屏障同步。线程在当前题的多个深度间会复用，不能误写成每个深度都重新创建。

egg 的 worker pool 在整批输入之间常驻，复用任务和缓冲区；任务按块领取，剩余工作少时减小领取块。线程空闲时可以向其他线程请求拆出尚未完成的子树，降低“多数线程结束，只剩一个线程做难题尾巴”的浪费。任务列表的扩展、排序也能由多个线程协作。

它还把早期几轮搜索中的部分工作安排得更连续，减少轮间空等；只有确认所有更短深度已排除后才报告解，所以没有以放弃最优性换速度。后续搜索利用上一轮统计调整任务优先级，尽早搜索更有希望的分支；我们也已有前缀排序，只是调度结构和细节不同。

这是与本机“16 线程合作解一题”直接相关的差异，但没有线程等待剖析或线程池单独开关测量，不能声称省下的 11.88 秒都来自线程创建。源码：egg [`src/lanes/share.rs`](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/src/lanes/share.rs) 模块说明和 `solve_all`；我们冻结版 `src/native_parallel.rs:189`、`src/main.rs:267`。

**六、为什么我们以前做了很多优化，还停在这里**

首先，过去并非没有成果。旧机器上的同轮系列记录中，Opt10 从 **33.032 秒到 24.591 秒**，约少用 **25.6% 时间**；Opt8 WASM 的正式四 worker 版本在当地测试从 **37.794 到 33.369 秒**，约少用 **11.71% 时间**。这些历史数字不能与这次 M5 Max 的 22.686 秒直接串成连续提速。

真正的问题是：后期很多尝试沿用原有搜索框架，着重增加更强的剪枝或局部缓存。数学上能少搜，不等于付出的执行成本划算。

| 我们的历史实验 | 实际发生什么 | 为什么不能当成功 |
| --- | --- | --- |
| Opt10 集中读取 8 个查询 | 查询量接近原版；25.145 → 29.764 秒 | 新组织方式慢约 18.4%，并非发出更多读就能更快 |
| Opt9 成功值缓存加根下界 | 大表查询约少 10%；46.634 → 47.911 秒 | 查询节省没有抵消组合改动的成本；不是缓存单因素因果测量 |
| Opt10 祖先证书链 | 约 1.417 亿次证书检查，仅 12,418 次实际强化 | 节点约少 0.33%，总时间反增约 3.63% |
| Opt10 替代对称投影 | 节点约少 1.20%、查询约少 0.59% | 筛选和计算成本使总时间反增约 3.70% |
| Opt9 三进制坐标小表 | 单独坐标微基准约快 1.21–1.29 倍 | 完整求解 43.231 → 47.140 秒，局部快没变成整体快 |

这些是具体实现、当时硬件和单轮样本上的结果，不是宣判相应数学思路永远无效。拒绝这些变慢的版本是正确决定；需要改进的是后续研究方向：在增加每节点工作前，先估算它最多能省多少，再考虑整个查表、状态和调度循环。

egg 自己也研究过我们的负结果。其公开清单直接列出 `2017YANR02/cuberoot.me` 和 `solver/experiments/cube48opt-rust`，逐项对照查表、四分之一转、BPMX、前缀调度、角块研究等。对我们的两条思路，它另作了尝试但没有并入成功代码：反向陪集规则在其已有结构中基本冗余；额外对称投影即使假设额外查询免费，能省的查询也不足以补偿真正实现的额外查表。因此它既继承了前人的成熟技术，也能利用我们已经记录下来的试错结果。[上游对我们仓库的分析](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/docs/reference/inventories/x-cube48opt-rust-inventory.md)

我们自己的原始记录：[Opt10 实验](../solver/experiments/cube48opt-rust/opt10-native-experiments.md)、[Opt9 实验](../solver/experiments/cube48opt-rust/opt9-native-experiments.md)、[Opt8 WASM 实验](../solver/experiments/cube48opt-rust/opt8-wasm-experiments.md)。

**七、对方也不是“一次性成功”**

作者 README 自述：在 48 核 EPYC / 94 GiB 云机上，让 AI 持续工作约五天，使用约 2,400 美元 Claude Code 额度和 400 美元 Azure 额度。这是作者自报，未审计账单。作者也明确把核心算法归功于 Korf、H48、cubeopt、nxopt、vcube 等已有工作。[README](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/README.md)

公开主分支的初始提交装入了大量既有开发结果。随仓库提供的档案保存 **478 条历史提交消息记录、151 个失败或中性分支末端、59 个归档分支末端**；这些类别有重叠，478 不是 478 个独立成功优化，也不是当前公开 Git 图中的同等数量提交。[历史索引](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/docs/history/README.md)

它经历了架构调整、数据复用、调度重写及大量小实验。部分早期微小收益后来被发现与代码摆放位置有关；后期用成对测试、不同代码布局、不同工作负载复核。最新两个由性能分析引出的实验也被拒绝：按字节读压缩表、把 lane 推进移出主循环，都没有获得净收益。[最终优化复盘](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/docs/performance/OPTIMIZATION_REVIEW.md)

这不能证明某个 AI 天生比另一个强。能从材料确认的是：它以一套新的整体实现承载优化，进行了密集实验，也保留大量失败结果；我们后期在原有结构内做局部增量，遇到了成本抵消收益的问题。

**八、对 Timer 和 64G 的实际含义**

线上 Timer 的阿里云服务器是 **4 vCPU、约 15 GiB RAM、7.78 GB Opt8 表**。本机结果来自 **M5 Max、16 搜索线程、31.13 GB Opt10 表**。因此这不是线上接口已经快了两倍，更不能将 64G 表直接用在现有服务器。

本轮线上试验已经说明，单点移植不能保证复制收益：8 通道交错版慢 14.27%，32 通道加空闲分配慢 10.70%，AVX2/POPCNT 编译候选慢 1.27%，NTA 预取近乎持平。T0 加动态分配第一组快 4.06%，但事先冻结的另一组题目反而慢 4.93%，因此未发布。候选保留了我们的坐标、状态生成和前缀框架，并非完整换成 egg 引擎。没有证据把失败仅归咎于 CPU，或把部分改写失败视为完整 egg 也一定失败。[实测与验收](timer-optimal-egg-tracker.md)

64G 是另一条已完成的收益路径：h10 保留 10 个独立棱朝向位，h11 保留 11 个，区分状态更细，表容量约翻倍，通常能提供更强下界。这仍是抽象下界，不是完整魔方状态的精确解表。固定 32 lanes 的旧、新表对照中查询减少 45.76%，求解从 10.804 到 6.547 秒；默认 24 lanes 为 **6.471 秒**。后者相对 egg h10 约少用 40.11% 时间，相对我们的 Opt10 约快 3.51 倍，但已经用了约两倍表容量。

64G 与历史 32G 运行之间关闭了开发服务，修改了 macOS 加载器，二进制也改变；搜索源码和相应构建设置保持，但不把这一对照称为严格单变量实验。后续按照用户约定只用 64G 默认 lanes，不再额外比较 32 lanes。

**九、后续研究应该怎样排序**

1. 保留已经完成的 egg h11 默认配置成绩；本轮只复查 h8，不追加 H11 加载、求解或建表。

尚不能回答的只有更细的因果分账：滚动流水线、状态表示、查询复用和工作共享，在本机这 2.10 倍中各占多少。现有证据足以解释设计方向和过去受阻的机制，但不足以给每项编造百分比。

作者 README 的 **3.9×** 确实指本仓库的 `cube48opt-rust Opt8`，不是前文另一行 `cube48opt10` 的成绩。其条件是 AMD EPYC 9V45、1 GiB 页、单线程；Opt8 约 1.044 s/题、egg 约 0.271 s/题。THP 对照仍约 3.7×，延迟模式也有优势。因此不能只说“模式不同”或“作者用了大页”就解释完差距。[上游完整比较](https://github.com/ArhanChaudhary/egg-solver/blob/947c20d93564f150aad9c292486ab730a329b86c/docs/comparisons/RESULTS.md)

**这次具体排查出了什么：**

1. **适配层不是几倍性能损失的来源。** 在 Mac 和服务器都运行了未改搜索的原版 CLI；其速度与适配版接近。我们没有把原版算法换成另一套慢搜索。
2. **初始服务器构建确实漏用了一个适用的指令集路径。** 通用 x86-64-v3 只启用 AVX2；实际 Skylake 服务器具备 AVX-512F/BW/VL，能走 egg 的额外路径。该路径不要求服务器缺少的 VBMI。固定同一上游源码和 Rust 1.98.1，改为 `target-cpu=skylake-avx512`，先在真实服务器通过两个小表测试，再测 100 题。时间从 81.381 降为 76.110 秒，约减少 **6.48%**；这修正有价值，但不足以把当前服务器结果变成几倍提速。交叉编译与原 CI 构建的宿主也不同，不能把整个差值精确归给一条机器指令。
3. **egg 在两台机器并没有多搜十几倍节点。** 原版 CLI 的节点总数：Mac 约 21.98 亿、服务器 AVX2 约 21.86 亿、AVX-512 约 22.05 亿，相差不到 1%；对应时间却是 6.49、81.38、76.11 秒。这把差异定位到执行这些工作的成本，排除了“云端搜索量暴增”的解释。不同引擎的节点定义不能直接比较，此处只比较同一个 egg 计数器。
4. **平台差异具体如何分账仍未测出。** Mac 的 4 个搜索线程与云机 4 vCPU 不等价；该 KVM 客机报告为 2 核、每核 2 线程，这不是宿主物理资源独占分配的证明。ARM / x86 生成代码、缓存、随机访问延迟、地址转换及共享硬件资源都可能影响收益。没有硬件事件和隔离实验，就不能断言是某一种缓存、SMT 或虚拟化独自导致。作者 EPYC、我们的 Xeon、这台 M5 Max 是三个不同环境。

因此，该轮结论是：本机的 8G 提升已实测成立；当时阿里云 Timer 保留已有 Opt8。随后用户授权的取证与有效优化见下一节，旧数据不变。

本机证据为 `.local-data/egg-h8-mac-20261109/{plan.json,report.json,diagnosis-verification.json}`；两个云端 CLI 目录为 `.local-data/egg-h8-aliyun-20261109/cli100/` 和 `.local-data/egg-h8-skylake-20261109/cli100/`。比较页的可下载 JSON 保存各二进制、原始结果与独立验解摘要。上游仍固定为 `947c20d93564f150aad9c292486ab730a329b86c`，本机只叠加已记录的 macOS 读表修复。

准备过程也保留了两处更正：Opt8 生成时摘要与线上表完全相同；复用验证凭据时误用了 `darwin` 而非 Rust 的 `macos`，加载器因此在另计的 3.909 秒启动阶段执行了自身验证，未另开全表扫描命令，求解时间不受影响。AVX-512 构建记录复制了旧 CI 的 `rustc host` 字段，已另存 `build-correction.json` 记录实际 Mac 交叉编译器；原始记录保留，二进制、目标和版本未变。上述问题均不隐藏，也不拿来解释性能提升。


**十一、云端为何变慢：预取方式与 Intel CPU 不匹配（2026-11-11）**

说人话：求解器一边搜索，一边提前把接下来要查的表数据搬进 CPU 附近。egg 的 x86 默认选择“尽量少占缓存”的搬法（PREFETCHNTA）。它在作者的 AMD 机器上有收益，但在我们这台 Intel 云机上吃了亏。我们改为普通缓存预取（PREFETCHT0），大幅降低了同一搜索工作的执行成本。表的内容、容量、最优性、默认 40 lanes、4 线程和调度算法均不变，Mac 的 ARM 代码也不受此补丁影响。

这不是看到 CPU 型号后猜出来的：

1. 先对加载完成后的搜索采样。egg 约 99% 的样本在 Worker::rounds 主循环，约七成集中在大表预取/读取的邻近指令；适配器、线程协调不是主要热点。软件采样的停顿位置可能落在下一条指令，不能把这些百分比直接称为某条指令独占的耗时。
2. 再做固定机器码布局的因果试验：原 AVX-512 二进制只改 **6 个字节**，把 6 条 PREFETCHNTA 改为 PREFETCHT0，其他字节和代码地址完全相同。带采样的 100 题时间由 **74.275352 秒降到 39.717867 秒**；搜索区间 CPU 时间由 263.97 降到 129.61 秒。
3. 两个 egg 进程在开始求解时实际占用的大页都是 **2,942,304,256 字节**，进程 swap 均为 0。没有换表、增大内存、改系统大页参数，也没有换题。因此本轮大幅变化不能归给大页覆盖率变化。
4. 固定布局程序只用于诊断，不上线。正式版本从固定上游源码重新编译，仅将 read_once 的 x86 分支改为 T0；真实服务器上的两项小表测试通过后，关闭采样，重新对照线上原 Opt8。最终结果如下。

| 无采样正式验收，WCA 1–100、4 线程 | 原 Opt8 | egg T0 | 变化 |
| --- | ---: | ---: | ---: |
| 100 题求解时间 | 72.907062 s | 36.391685 s | 时间减少 50.08%，速度 2.0034× |
| 搜索区间 CPU 时间 | 250.39 s | 128.31 s | 减少 48.76% |
| P50 | 0.463452 s | 0.223277 s | 减少 51.82% |
| P95 | 2.801523 s | 1.569502 s | 减少 43.98% |
| P99 | 4.258566 s | 2.016838 s | 减少 52.64% |
| 独立回放、历史最优步数一致 | 100/100 | 100/100 | 全部通过 |
| 5 秒空闲 CPU 时间 | 0.00 s | 0.00 s | 无忙等 |

每版一轮、不预热、顺序逐题，读取大表的启动时间另计；这不是 HTTP 或排队延迟。新 Opt8 基线独立重新测量，没有拿 10 月 22 日更慢的 87.98 秒作分母。每一项验收门槛沿用旧计划：总时间至少减少 10%、CPU 不增加、中位数不超过原版 105%、P95 不退步、P99 不超过 105%、空闲 CPU 不超过 0.1 秒。全部通过。

**为什么 T0 合理，哪些细节还不能下结论？** Intel 官方优化手册第 9 章明确说明预取提示的实际行为随微架构变化；Skylake / Xeon 的 T0 与 NTA 在 L2 填充、L3 替换策略等方面不同。T0 更适合让随后需要的数据留在普通缓存层级。这与我们的指令替换试验一致。但该 KVM 客机不开放硬件 cycles/instructions 计数器，不能把时间减少进一步精确拆成 L2 命中、TLB、队列阻塞各占多少，也不能虚构缓存未命中率。[Intel 官方手册，第 9 章](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf)

**为什么之前优化没见效？** 原来的很多实验调整的是剪枝、状态表示、批量推进，增加了每节点工作却没有保证足够的搜索节省；这次则找到正在浪费时间的底层内存访问提示，并用单变量机器码试验确认。只看“少搜了多少节点”，或者把所有差异笼统归给云服务器慢，都可能漏掉这个问题。原 Opt8 自己已使用 T0，因此它没有同样的 NTA 损失。egg 的其他搜索组织优势在移除这个成本后才在云端体现出来。

**为何云端 2 倍而不是 Mac 的 3.44 倍、作者的 3.9 倍？** 三者的 CPU、缓存、线程资源和运行条件不同，不能要求相对倍数完全一致。我们已经确认并修掉一个造成云端退步的主要原因；剩余平台差距没有逐项量化，不用硬件名词编造确定分账。单轮 100 题证明的是这台服务器、本组题和当前配置的收益，不承诺每一题都快两倍。
