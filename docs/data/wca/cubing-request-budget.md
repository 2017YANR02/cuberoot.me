# Cubing China 请求合并与刷新策略

2026-11-14 本地实现；尚未发布或测量线上降幅。入口为
`core/apps/api/src/utils/cubing_source.ts` 与 `cubing_stream.ts`。

API 进程内的比赛页、预热、纪录监控、复盘成绩导入及分组奖项共享按上游 URL
缓存的响应和在途请求。缓存最多 2000 项、约 32 MiB 字符串存储，HTTP 并发最多 3。
每个消费者独立解析 JSON，个人纪录补充及轮次编号转换不修改公共快照。
离线统计任务仍使用 shared 中的原始读取器及自己的缓存。

| 数据/入口 | 策略 |
| --- | --- |
| 完整比赛目录 | 共享 2 分钟；根据显式 WCA ID/alias 判断是否收录 |
| 比赛信息、报名表、领奖台 | 5 分钟；直播事件可提前失效 |
| 进行中比赛的后台纪录监控 | 保持每分钟一次，按北京时间起止日判断，覆盖多日赛 |
| 结束不超过 2 天的后台纪录监控 | 每 15 分钟 |
| 更早、结束不超过 30 天的后台纪录监控 | 每 6 小时 |
| 后台轮次结果 | 活跃轮次 5 秒、当天已完成轮次 1 分钟；结束后按上述时间分档 |
| 前台轮次、复盘成绩导入 | 最多复用 5 秒成绩快照，不受后台历史缓存时长限制 |
| 不存在的比赛详情 | 404 缓存 1 小时；目录出现该比赛时提前清除 |
| 不存在的附属资源 | 404 缓存 1 分钟，不能把未开放直播误判为比赛不存在 |
| 429 / 503 | 遵守 Retry-After；429 至少全局退避 1 分钟，普通暂态失败缓存 10 秒 |

正在观看同一比赛的所有观众共享一个上游 SSE 连接。转发事件前使受影响轮次缓存失效；
无法定位轮次时使整场失效，重建上游连接时也刷新整场。最后一位观众离开时断开上游。
慢消费者有队列上限，断线后浏览器仍使用原有 15 秒轮询兜底。一个观众断开不能取消
其他观众的请求；失效之前的在途响应不能覆盖更新后的缓存。

预期用户影响：直播事件驱动的刷新保留；轮询兜底可能额外复用最多 5 秒数据。
新比赛发现增加最多约 2 分钟目录缓存等待。无人观看的历史比赛订正及相关后台通知
按 15 分钟/6 小时分档同步，通知发送失败仍按分钟重试。页面功能与公开端点保持一致。

验证使用本地 fixture 和 mock 上游，不请求 cubing.com：覆盖多人合并、缓存数据隔离、
删除/订正、在途失效竞态、直播断开、负缓存、Retry-After、跨日比赛与后台扫描节奏。
上线后的真实降幅需用同窗口出站请求或粗饼侧日志确认，不能用本站访问量直接替代。
