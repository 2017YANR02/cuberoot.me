# Agent 分层上下文真实模型对照（2026-11-15）

状态：本地验证，未提交、推送或部署。仅评估项目站内 Agent；没有调整 Codex 的上下文、配置或记忆。

Memory Graph 在本组场景中改善了旧信息召回，完整达标从 **15/24 提升到 21/24**，实际总 token 减少 **10.1%**。但耗时中位数和 P95 均变慢，且 token 节省集中在少数场景，**不能得出整体提速或普遍降本的结论**。当前适合继续优化和扩大验证，不应把本报告当作发布验收。

## 对照口径

- 基线提交：`b625db4d191694184b2c9677d381cef0e8c676e0`。候选为本地 Memory Graph 与分层编排实现，见[设计合同](../assistant-design.md#memory-graph-与分层上下文)。评测期间未修改两版运行时代码。
- 模型：现有已配置的 `deepseek-flash`，`auto` 模式；保留真实 Agent 的工具调用、快／深模式切换、证据复核及失败重试。没有用 mock 模型或额外评委模型。
- 12 个预设场景，每版每题 2 次，共 48 条正式样本、24 对比较。每题交替 AB/BA，第二遍反转顺序；串行执行，供应商缓存不清空。
- 两版使用相同的合成完整对话。基线沿用最近 10 条消息、40,000 字符边界；候选另从同一历史构建会话图，模拟历史请求已积累的状态。图预建在计时前完成，没有引入历史以外的答案或用户资料。
- 所有资源请求使用同一批已校验 SHA-256 的公开快照：百科、页面／正文索引、公式目录、PLL 与 F2L。百科和索引快照来自 11 月 13 日，两个公式集合在本轮获取。远程向量检索、reranker、联网搜索关闭，页面本地词法检索仍可使用冻结索引；不覆盖完整生产 RAG 链路。
- 耗时从进程内 Agent 请求开始到返回，包括工具执行、模型重试与本轮记忆更新；不包含浏览器、HTTP 入口、数据库祖先恢复、历史图预建和真实上游网络耗时。首次答案时间为首个 `answer` 事件；非流式答案用最终返回时刻，失败无答案的请求不进入该项分母。这不是供应商原始首 token 时间。
- token 来自每次供应商响应的实际 usage，包含工具循环、复核、重试及缓存命中的输入；不以工程估算代替计费口径，也不把命中缓存的 token 从总量扣除。
- 质量由执行本任务的 Agent 按调用前保存的题目准则逐条审阅：2 分完整达标，1 分部分完成／诚实说明缺口，0 分错误、答非所问或无答案。不是独立人工盲评；评分理由逐条保存，完整达标率不包含部分分。

这些是开发场景，不是独立留出集。长历史场景含重复填充文本，模拟窗口压力，不能当作真实用户流量分布。两次重复不足以估计稳定的线上 P95 或统计显著性。

只看两版都完整达标的 15 对，token 减少 **4.1%**，平均耗时反而增加 **10.8%**。去掉 C08 后，总 token 几乎持平：476,137 → 475,647，减少 **0.10%**。这些是补充分析，主结果仍包含全部样本。

## 场景结果与未解决问题

每行每版 2 次；耗时为两次平均，token 为两次总和。

| 场景 | 完整达标：前 → 后 | token：前 → 后 | 平均耗时：前 → 后 |

| C01 最近阶段顺序追问 | 2 → 2 | 24,668 → 25,302 | 0.85 → 0.89 秒 |
| C02 长历史后切换到翻译 | 2 → 2 | 42,340 → 34,516 | 0.83 → 0.79 秒 |

| C12 强相关长对话保留最近阶段 | 2 → 2 | 42,274 → 42,273 | 0.80 → 0.82 秒 |

有效改善与边界：

- **窗口外召回**：C04 候选两次准确回答 `KITE-42`；基线只能请用户重述。C08 候选两次正确恢复“只观察角块、不转层”和“定位对应棱块”；基线一次检索报错，一次转为通用训练建议。C08 少走了无效检索路径，是本组大部分 token 节省的来源。
- **话题切换**：C02/C03 均保持 4/4 达标，两版总 token 从 84,756 降至 69,096，减少 18.5%。候选仍有旧窗口摘要成本，并非无关历史全部消失。
- **约束召回不等于严格执行**：C05 候选两次都恢复了 12 分钟、不计时、不学新公式，但第二次追加“3～5 次完整还原”，没有限定这一环节必须慢拧，不能严格满足“只做慢拧和观察”，按部分分计。需要后续验证最终回答对约束的遵守。
- **共同的核验缺口**：C11 两版各两次都返回“现有证据未能支持可靠结论，暂时无法确认”，没有给出所需定义和引用。冻结百科 `wiki:219` 的标题包含 “F2L (First Two Layers) 前两层”，正文为空；不能把正文为空直接等同于无法回答标题已明确的信息。候选此题还更慢。需要单独追踪工具选取、证据匹配和最终复核，当前证据不足以把原因归结为图记忆。
- **短上下文开销**：C01 候选每次实际输入多 317 tokens。它被判为弱相关，通过活摘仍找回正确阶段，但这不证明相关性分类准确覆盖了全部指代。强相关长历史 C12 则基本没有 token 节省，符合保留完整最近对话的取舍。
- **重试波动**：C07 基线 3 次、候选 4 次模型调用，包含空输出后的已有重试。不能把其全部耗时差都归因于上下文长度。
- **编排前的资源读取**：C03 即使已经切换到做菜，两版仍因历史里的 PLL 先读取公式集合；C06 也会读取 F2L 集合。源码 `site_assistant.ts` 在模型编排前调用 `resolveAssistantAlgorithmRequest(question, history, ...)`。当前强／弱相关窗口主要影响模型输入，尚未统一影响这些前置历史解析路径。

## 下一轮优化顺序

1. 将当前主题判定复用到前置历史解析与工具预取，先处理明确的话题切换；保留真实公式追问的兼容性。
2. 对已进入最近完整对话的短信息进一步去重，减少短问题的图元数据与摘要开销；不压缩系统提示词和当前需求。
3. 追踪并修复 C11 的标题证据利用和复核拒答，控制无收益的复核循环；单独确认 C05 的严格约束遵守。
4. 使用新增、未用于开发调参的真实或脱敏对话扩大测试；覆盖跨日期、多主题、不同语言、过期记忆和更长历史。将数据库恢复、真实 RAG、上游网络与浏览器首屏时间纳入后一阶段测量。

本轮只完成评测脚本与记录，没有依据这批答案继续改动候选运行时代码，也没有发起发布。

测试结束后的工作区核对发现 `site_assistant_tools.ts` 及新增统计元数据相关文件出现快照外修改；它们不属于本轮评测变更，已原样保留。报告只验证上述冻结候选，不代表后来工作区的全部代码。`validation.json` 保存最后的差异核对；本轮脚本在运行后另补了资源保护触发后的持续停止检查，实际执行版本仍保存在 `runner.mjs`。
