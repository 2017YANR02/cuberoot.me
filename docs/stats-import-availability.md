# Daily statistics imports and online availability

## Incident and scope

On 2026-09-12 at about 00:20 UTC, ten API database connections were waiting for
relation locks held by the historical-ranks import. The blocking session was
copying the monthly snapshot, but its transaction had already truncated
`wca_persons`, countries, and the other snapshot tables. Those exclusive locks
lasted until the entire import committed. The shared API pool was exhausted,
including the small `home_card_locks` read used by page access verification.
The Web proxy consequently returned its five-second verification-unavailable
503, including for administrators.

This change covers the daily `stats.yml` historical-ranks import, its appended
historical SOR import, and the WCA stats-extra full/incremental paths. It does not
change page authorization, cache stale permissions, or enlarge the API pool.

## Import contract

- `pg-refresh.ts` owns the job-local SQL protocol. Typed temporary COPY input is
  checked for expected row count and duplicate logical keys. Only changed rows
  are updated; missing rows are inserted and removed rows deleted. Online table
  OIDs, indexes, grants, defaults, generated columns and dependencies remain.
- A logical key need not be a physical primary key. Monthly history retains its
  existing non-unique lookup index; duplicate live logical keys cause rollback.
- The data and its import timestamp commit together. SELECT continues to read
  the previous committed version until that commit. Refresh writers serialize
  using a shared advisory transaction lock and reader-compatible table locks.
- Compatibility DDL is confined to separate short schema transactions with a
  bounded lock wait. Already-present compatibility columns do not execute ALTER.
- Keyless aggregate/full tables retain their duplicate-row semantics through
  transactional DELETE/COPY. Incremental competition fingerprints and final row
  counts remain checked; a failure rolls back that data transaction.
- Hash joins are disabled only within the indexed comparison/refresh blocks and
  the previous setting is restored. A local 250,000-row comparison showed the
  history UPDATE spilling about 61.5 MB with a hash join and zero with an ordered
  join. This is not a production-scale throughput guarantee.
- A stage created in the current transaction is explicitly truncated through
  `pg_temp` before it is dropped. PostgreSQL can free those new temporary files
  in place. DROP alone defers file removal until commit and would accumulate
  every stage's disk usage. No online table is truncated.
- Post-commit maintenance is ordinary VACUUM (ANALYZE), never VACUUM FULL.

## Space admission and production boundary

`pg-import-capacity.ts` checks the filesystem containing `load.sql` before
staging, then checks the actual new/changed/deleted rows before keyed writes.
Keyless full and delta imports have separate estimates. The estimates reserve
1 GiB for other activity and account for temporary indexes and additional WAL.
They are admission estimates, not quotas or guarantees against unrelated disk
growth. The import directory, PostgreSQL data, temporary tablespace and WAL must
be on the same filesystem; this was verified for the incident server.

The former fixed 4.5 GB historical-import gate is replaced by these per-table
checks. Insufficient space fails the import and rolls back; it does not justify
deleting production files. Server cleanup remains an operator decision.

Pushing code runs the stats syntax check and the applicable Test workflow. It
does not execute a full statistics rebuild. The next scheduled or explicitly
authorized dispatch produces the updated `load.sql`. Do not report a local
fixture or a code push as evidence of a completed production data import.

## Verification

From `core/`, with an isolated loopback PostgreSQL test database:

```sh
STATS_IMPORT_TEST_PG=1 PGHOST=127.0.0.1 PGPORT=55439 \
  PGUSER=postgres PGDATABASE=cuberoot_stats_test \
  pnpm --filter @cuberoot/stats-build test
pnpm --filter @cuberoot/stats-build typecheck
pnpm --filter @cuberoot/client exec vitest run \
  tests/home_card_route_access.test.ts tests/wca-calculators-port.test.ts \
  tests/workflow-path-contract.test.ts
pnpm audit:boundaries
```

The PostgreSQL tests execute the generated psql/COPY artifact. Coverage includes
sixteen concurrent reads and permission reads, old/new snapshot visibility,
REPEATABLE READ across commit, typed COPY/count/constraint failures, unchanged
row versions on repeat imports, stable dependencies, simultaneous importer
rejection, space rejection, and pre-commit physical temporary-file reclamation.
The complete six-table historical-ranks artifact is generated by
`historical-ranks-load.ts` in both production and tests. CI runs against PG 13;
the incident's local tests used PG 16.15.

For producer/upload parity, historical COPY references now live in
`src/historical-ranks-load.ts`; include the appended
`sor_historical_best.copy.tsv` from `sor_over_time_build.ts`. The seven inputs
must match the explicit `stats.yml` upload list. Stats-extra still uploads all
generated files through its existing wildcard.
