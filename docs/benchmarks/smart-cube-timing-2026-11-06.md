## 比较口径

这是计时准确性基准，不是吞吐量或页面性能测试。真实时长由生成器的独立 `realMs` 给定，两种算法只能看到设备时间与接收时间。

两边均从已预备状态开始，关闭观察、多阶段计时和专项训练；起止定义为首个动作报告到最终动作报告。完成状态由测试指定，不验证魔方状态推演、UI 或数据库保存。

CubeRoot 调用公开包出口的真实 `MoveClock` 与 `transitionTimer`，最终成绩来自 `stop-from-cube` 返回的 `solve.timeMs`。不重新实现算法，也不只比较未经起停限制处理的时间差。

csTimer 从固定原文件提取并执行以下函数的原始文本：

- [`tsLinearFit`、`tsApplyFixes`、`tsLinearFix`](https://github.com/cs0x7f/cstimer/blob/103f4c2ccdddc0d0c3a574aac1f3e378d02a06e5/src/js/tools/bluetoothutil.js#L421-L488)
- [`giikerCallback`、`isGiiSolved`](https://github.com/cs0x7f/cstimer/blob/103f4c2ccdddc0d0c3a574aac1f3e378d02a06e5/src/js/timer/giiker.js#L189-L299)

外围替身只提供 UI 空操作、完成状态、计时存储访问器和结果捕获。最终成绩必须由真实回调发出的 `time` 信号取得，且与实际校正序列末项相同。每局必须恰好发出一个成绩；不能用旧硬件对拍环境中的 `tsLinearFix: a => a`。

上游文件与各函数的 SHA-256 均在 JSON 中。源码只读缓存，不修改受保护的 `/cstimer`；站点现有 csTimer 致谢继续复用。

## 场景覆盖

| 分组 | 数量 | 输入 |
| --- | ---: | --- |
| 固定漂移 | 28 | −5%、−0.7%、−0.1%、0、+0.1%、+0.7%、+5%；5／10／30／60 秒；固定 20 ms 接收延迟 |
| 传输变化 | 364 | 上述漂移和时长，叠加 8 组固定种子的 8–100 ms 抖动、每批 4 手、首包／末包额外延迟、线性增长延迟、局中阻塞 |
| 连续连接 | 36 | ±0.7%、±5%；预运行 10–600 秒，包括阈值前后；同一个 MoveClock 持续接收动作后测量 10 秒 |
| 阈值边界 | 4 | 正常时钟，末包额外延迟 1999／2000／2001／2500 ms |
| 无设备时间 | 3 | 使用接收时刻，末包额外延迟 0／100／2500 ms |
| 时间原点 | 6 | 同一组间隔，只改变设备与主机时间戳原点；包含接近 32 位上限但没有回绕的计数器 |

默认每 100 ms 一手，包括首末两手，所以 10 秒有 101 个报告。设备 elapsed counter 先按整数 ppm 计算并量化为毫秒，再加原点，避免输入生成器自身的浮点舍入混入原点比较。9 项内置检查包含各原点版本逐步间隔完全相同、随机种子复现、真实校正非直通、输入不被修改以及实际成绩信号捕获。

批量模型中，同批老动作没有独立的主机时间观测，只有最新一手给 csTimer 的 `localTs`；最后不足四手的一批立即冲出。两边收到同一批动作与同一到达时刻。这是明确的解码后回调模型，不代表所有硬件协议的批量处理方式。

## 主要结果

以下真实动作间隔均为 **10.000 秒**，负误差代表成绩偏小。

| 条件 | CubeRoot | csTimer | 说明 |
| --- | ---: | ---: | --- |
| 正常时钟、固定延迟 | 10.000 s | 10.000 s | 基本对照 |
| 时钟慢 0.7% | 9.930 s | 10.000 s | CubeRoot 保留了设备比例误差 |
| 时钟慢 5% | 9.500 s | 10.000 s | 同上 |
| 时钟快 0.7%、刚开始 | 10.000 s | 10.000 s | CubeRoot 的未来时间截断掩盖了原始 10.070 s，不代表做了速率校正 |
| 慢 0.7%，先运行 280 秒 | 11.931 s | 10.000 s | 局中重新定锚导致跳变 |
| 末包额外迟 2000 ms | 10.000 s | 10.115 s | CubeRoot 尚未触发重新定锚 |
| 末包额外迟 2001 ms | 12.001 s | 10.116 s | 多 1 ms 延迟触发整体 2001 ms 的偏移 |
| 首包包含四手、最后一批仅一手 | 9.700 s | 10.000 s | 首次定锚偏后 300 ms，末手未来时间被截断 |
| 延迟从 20 ms 线性增长到 120 ms | 10.000 s | 10.100 s | csTimer 将时间相关的传输延迟吸收到拟合斜率 |
| 无设备时间，末包额外迟 100 ms | 10.100 s | 10.100 s | 两边均无法恢复设备实际动作时刻 |

### 漂移与重新定锚如何共同产生 11.931 秒

用例 `age/-0.007/280000` 中，首末设备时间差为 9930 ms。计时从连接后 280000 ms 开始；到 285800 ms 时，映射时刻落后接收时刻 2001 ms，超过 `RESYNC_THRESHOLD_MS = 2000`。实际 `MoveClock` 在这一手将时间轴向前移动 2001 ms。

因此最终间隔为 `9930 + 2001 = 11931 ms`。轨迹中起停截断量均为 0，误差可明确归因于局中的定锚变更。只在每局创建新 MoveClock 的测试会漏掉这个问题。

### csTimer 的数值边界

`numeric-origin` 六个用例的设备间隔、到达间隔逐项相同，均为 +0.7% 时钟、预运行 600 秒后测量 10 秒。仅平移时间戳原点：

| 设备原点 ms | 主机原点 ms | csTimer 成绩 |
| ---: | ---: | ---: |
| 0 | 0 | 10.000 s |
| 0 | 1700000000000 | 10.000 s |
| 1000000 | 0 | 10.000 s |
| 1000000 | 1700000000000 | 9.998 s |
| 4000000000 | 0 | 9.994 s |
| 4000000000 | 1700000000000 | 6.882 s |

原函数用 `n * sumXY - sumX * sumY`、`n * sumXX - sumX * sumX` 计算斜率。大数相减会丢失有效精度；纯原点平移实验说明结果不满足本应成立的平移不变性。该结果来自原始函数，不能据此推断某品牌或 csTimer 当前网页上已实际发生这些错误；各协议是否重置／展开设备计数器尚未纳入本轮。

### 分组统计

不把所有场景混合后的平均值当作实际用户精度；正负误差会抵消，合成条件也不是用户出现频率。

| 分组 | CubeRoot 绝对误差 P95／最大 | csTimer 绝对误差 P95／最大 |
| --- | ---: | ---: |
| 固定漂移 | 995／1500 ms | 0／0 ms |
| 传输变化 | 995／1500 ms | 100／102 ms |
| 连续连接 | 1931／1931 ms | 2／2 ms |

P95 为 nearest-rank，尤其四个阈值样本的 P95 就是最大值。JSON 的 `casesWithin10Ms` 只用于筛选，不是已确认的产品验收标准。

本轮确认需要处理的是：设备速率校正、单局时间轴连续性、首批延迟与未来截断的配合。后续候选算法应在同一语料上增加比较列，使用数值稳定的拟合，并防止延迟趋势污染速率估计；不按品牌硬编码修正比例，也不直接把 csTimer 原实现当作标准答案。

尚未覆盖：设备解码、传感器阈值、实际 BLE、漏步及估算时间、计数器回绕、局中断连、纯状态恢复停表、浏览器系统时钟调整、多阶段／专项训练、真机和生产验收。用户本轮要求是建立软件基准，产品修复另行推进。
