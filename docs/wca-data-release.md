# Latest WCA data

The code and generators remain in this repository. Five generated files are published as attachments to the single mutable [`wca-data-latest` Release](https://github.com/2017YANR02/cuberoot.me/releases/tag/wca-data-latest):

- `stats/nemesizer/persons.bin.gz`
- `stats/nemesizer/ranks.bin.gz`
- `stats/nemesizer/counts.bin.gz`
- `stats/nemesizer/meta.json`
- `stats/persons_search.json.gz`

The same Release also contains one latest statistics snapshot: generated root JSON, competition calendar/city data, records, rankings and generated scramble statistics/downloads. Tutorial media, solver tables and server-only competition/step shards retain their existing owners. Historical results inside the latest dataset are preserved; obsolete export versions are removed. SQL computation is unchanged. Authorized Git history maintenance is recorded in the tracker.

## Local development

From the repository root, with the pinned Node version and an authenticated GitHub CLI:

```sh
node scripts/wca-data/cli.ts hydrate
node scripts/wca-data/snapshot-cli.ts hydrate
```

This downloads the current archive, checks its inventory, gzip integrity and SHA-256 hashes, then restores ignored local files. It does not compute statistics, load solver tables, or modify production. A clean checkout can run unrelated development without these files. Local Nemesizer API development can continue using `NEMESIZER_DATA_DIR` pointing at the hydrated `stats/nemesizer` directory.

Statistics hydration records `stats/.stats-release-base.json`. Hydrate before computing; differing local files are rejected rather than overwritten. Preserve the baseline with unfinished local work. From `core/`, `pnpm stats:hydrate` restores the statistics snapshot. CI explicitly uses replacement hydration in disposable checkouts.

## Publishing

The existing Update Stats workflow generates the five files, then `submit` uploads a uniquely named candidate and dispatches **Publish WCA data**. Its publish job shares the `deploy-core-production` concurrency group with API deployment. Standard hosted runners and Release attachments are used; there is no new paid storage service or permanent Actions artifact.

The single Release's JSON body is the current manifest. It records source commit, export/generation dates, counts, file hashes and archive identity. An archive is uploaded before it becomes current. Production stages and validates it, switches the complete data directory, confirms the API's loaded generation and public static file bytes, and only then advances the Release body. An uncertain GitHub response is resolved by reading back the body; if GitHub is unreachable, the live data and journal remain for recovery.

The publisher removes the completed candidate manifest and the previous current archive after success. Queued candidates are temporary and are not daily releases. Abandoned candidates older than 24 hours are removed at the next successful publication; active queued candidates are preserved. Never mark this Release immutable or use it as the application's latest software release.

Statistics producers submit owner-scoped patches through `node scripts/wca-data/snapshot-cli.ts submit OWNER`: `wca`, `upcoming`, `elevations`, `scramble` or `world-bests`. The publisher merges each patch into the latest snapshot under the same deployment lock. Conflicting same-file edits fail before mutation; independent updates merge, and the append-only elevation cache unions coordinates while rejecting conflicting values. Competition calendar shards are rebuilt from the merged past/upcoming inputs. Producers no longer commit data or push Git. Successful publication retains one binary archive and one statistics archive in this single Release, and removes completed patches and old snapshots. Abandoned statistics patches expire after seven days.

During initial adoption, `sourceCommit` identifies the publisher code that packaged the existing server files, not a claim that those files were regenerated by that commit. For subsequent Update Stats submissions, it identifies the checkout that generated the candidate. The export date and generation time always come from the actual dataset metadata.

For initial adoption or an idempotent re-publication of the current server data:

```sh
gh workflow run wca_data_release.yml --ref main -f candidate=server
```

This does not regenerate data. Do not invoke the production publisher directly from a local terminal: it requires the serialized workflow. Do not bypass the queue with a separate rsync or API restart.

## Recovery and boundaries

- Deployment owns only `stats/.wca-data/`, the `stats/nemesizer` link, and the `stats/persons_search.json.gz` link. It never deletes or replaces sibling datasets, especially server-owned `stats/comp/`.
- Statistics deployment separately owns `stats/.stats-data/` and only the managed public paths listed by `scripts/wca-data/snapshot.ts`. It checks live hashes before switching, journals the transaction and verifies public bytes. Toolkit sync publishes only authored tutorial assets under `stats/`; local scramble static sync excludes Release-owned paths and never swaps the whole scramble directory.
- Before switching, the previous data remains local. A failed activation restores it and verifies the API reload. After the Release commit is confirmed, finalization removes previous datasets and adoption backups.
- `transaction.json` records interrupted activation. On the next workflow run, the publisher compares the journal with the Release manifest: committed data is finalized; uncommitted data is rolled back before retrying. No protection baseline is reset and no computation is restarted.
- A network failure while downloading can race a newer publication deleting an obsolete archive. Retry hydration to obtain the new manifest; never accept unverified or incomplete data.
- Ordinary browser/NGINX cache policies remain in force. Publication checks the origin API and a uniquely addressed static request; a pre-existing cached response is not evidence that the new server dataset failed to load.
- Git ownership checks reject reintroducing migrated files or retired bundles. History cleanup, retained offline backups and recovery of old checkouts are documented in the tracker.
