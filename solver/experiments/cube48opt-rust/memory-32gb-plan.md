## 本轮 H10 预算

H10 采用一次只读映射，包含主表与两个辅助段。受控验解预算为 31,141,620,584 字节（表加 768 MiB）；顺序对照预算为 31,410,056,040 字节（表加 1 GiB），均低于 32,000,000,000 字节，但这是进程树预算。启动另留 3 GiB，运行保守余量至少 2 GiB。表文件容量与求解器原生 RSS、监控树 RSS 分别记录；原生峰值由正式基准的 time -l 采集。

Rust 默认启动时校验完整分布，会触及整张映射；原 C 包装默认只 mmap，故峰值 RSS 包含不同启动行为。正式速度只比较完整预热后的搜索耗时，不把加载扫描计入搜索，也不把峰值差异直接归因于语言内存效率。本轮完整 60 例同表、单线程对照，排除加载与预热后的三轮整批总时间中位数为 Rust 36.782246953 秒、原 C 57.605142 秒，速度比 1.566112643 倍，耗时减少 36.1476%。960 条求解结果验解通过，其中 360 条正式计时，另有 8 次启动检查；Swapouts 为 0。

正式基准由 `time -l` 记录的原生进程最大 RSS 为 Rust **30,342,217,728 字节**、原 C **30,342,397,952 字节**；这是本次加载与固定语料求解的实际峰值，不是所有输入的内存上界，也不等于监控进程树采样值。协议、逐轮时间及重复性边界统一见 [性能与内存](benchmark-results.md)。约 32 GB 是进程档及保护预算，不是 32 GB/32 GiB 整机可运行保证。

## 假设的自有 EO10：目标与容量

若在 Opt9 的 9 个 EO 位上再保留 1 位，沿用现有填充坐标和每项 2 bit 编码，计划表容量为 **31,130,910,720 bytes = 31.130910720 GB = 28.992919921875 GiB**。这只是容量推导，不证明新表已存在、编码下界正确或搜索更快。GB 为 10^9 bytes，GiB 为 2^30 bytes。

现有 nissy-core H10 是 **30,336,314,216 bytes = 30.336314216 GB ≈ 28.252894260 GiB**。计划表比它大 794,596,504 bytes（约 2.619%），两者坐标与文件格式不同，不能互换。它们可以作为相近表容量的不同引擎对照，不能称为同表对照。

公开固定上游只提供 Opt1–9，没有可用于逐字节核验的 **Opt10 WASM、表、checksum 或最大下界**。新档应标为自有研究档，例如 EO10，不能冒称已恢复上游 Opt10。

计划坐标容量为 124,523,642,880 项，索引需要 37 bit；其中有效项按当前 padding 规则推导为 120,389,068,800。`Vec<u32>` 需 7,782,727,680 个元素，元素编号也超过 u32。现有 `u64` 坐标和 64 位 `usize` 足够表示，不能把存储元素类型 u32 与索引类型混为一谈。

## 32 GB 整机与 32 GB 进程的区别

| 条件 | 只扣计划表之后的剩余空间 | 含义 |
| --- | ---: | --- |
| 整机 32,000,000,000 bytes | 869,089,280 bytes | 还没有扣系统、应用、监控器、小表、栈和分配器；不满足现有启动保护 |
| 整机 32 GiB | 3,228,827,648 bytes，约 3.0071 GiB | 同样还没有扣系统和其它进程；现有单引擎预检已经要求超过 32 GiB 可回收内存 |
| 原生进程 RSS 上限 32 GB，宿主另有足够内存 | 表之外约 869 MB | 可能容纳一个紧凑实现，但必须实测额外开销，不能只按文件大小保证 |
| 原生进程 RSS 上限 32 GiB，宿主另有足够内存 | 表之外约 3.229 GB | 容量余量较大，仍需实际 RSS 与宿主保护同时通过 |

Opt 加载器在 [src/table.rs](src/table.rs) 直接向一份 `Vec<u32>` 流式读取，每次最多 4 MiB，不另造整表字节副本；`resize` 初始化后会实际触及整份分配。这不是只映射而按需驻留的小 RSS 模式。Rust H10 的 [src/h10_table.rs](src/h10_table.rs) 与原 C 的 `solver/native/solve_h48_h10.c` 都使用只读 mmap，但 Rust 默认还扫描完整分布；文件大小和实际驻留页不总相等，比较峰值或耗时时应保留加载校验、冷启动和预热差异。

下表是把当前 guard 公式外推到计划表的**预算**，不是已测峰值，也不是已经获准运行新档。预检在进程树预算之外再要求 3 GiB 可回收余量；运行中还检查压力、Swapouts 和至少 2 GiB 估计余量。

| 动作 | 进程树 RSS 预算 bytes | 预算 GiB | 启动所需可回收内存 bytes | 启动 GiB |
| --- | ---: | ---: | ---: | ---: |
| 单引擎：表 + 768 MiB | 31,936,217,088 | 29.742919922 | 35,157,442,560 | 32.742919922 |
| 顺序基准：表 + 1 GiB | 32,204,652,544 | 29.992919922 | 35,425,878,016 | 32.992919922 |
| 按现生成布局：表 × 18/16 + 768 MiB | 35,827,580,928 | 33.367034912 | 39,048,806,400 | 36.367034912 |

进程树预算包含监控器和包装运行时，不能当作纯原生进程 RSS。原生峰值由已限定原生入口的 `CUBEOPT_MEASURE_RSS=1` / `/usr/bin/time -l` 另行测量，输出与 guard 采样记录分别保留。拥有 64 GiB 物理内存也不等于当前有足够可回收内存；是否启动必须看当时观测，不关闭其它应用腾空间、不重设保护基线自动重试。

## 生成峰值是独立约束

沿用已恢复的上游生成布局时，EO10 的单份 frontier 为表的 1/16，即 1,945,681,920 bytes。压缩时新旧 frontier 短暂并存，再加主表、约 19.2 MB fast-move 对象、线程栈、动态向量和分配器，所以生成不能按求解占用估算。18/16 只表示主表加两份最大 frontier；768 MiB 是额外预算，不是对未来 Rust 生成器的峰值证明。

不能直接用每状态一字节的完整距离数组：连有效项就有约 120.39 GB，按填充坐标存储则约 124.52 GB；全量 `HashSet` 或宽整数队列会更大。新生成器必须先设计有界前沿、紧凑状态编码及释放/压缩顺序，再分别测构建与加载峰值。原 Opt8/9 WASM 的 16 GiB 最大线性内存甚至小于计划 PDB 本身，不能直接通过调整 JS 上限让原 WASM 生成这张表。

## 当前代码不能直接选择第十档

- [src/table.rs](src/table.rs) 的 `Variant::new` 只允许 1–9，checksum 数组也只有九项。
- [src/main.rs](src/main.rs)、[src/coord.rs](src/coord.rs)、[variants.mjs](variants.mjs) 和 [guard.mts](guard.mts) 均显式限制现有档位或布局。
- [src/search.rs](src/search.rs) 只接受最大下界 10–13，该值还控制 NISS 切换、前缀队列和排序尺度；不能未经证据猜测新档最大值为 13 或 14。
- 新表必须满足搜索器的特殊契约：正逆状态下界可采纳，并且对侧半转不变。任意更强的可采纳下界不自动满足半转缓存和动作剪枝所需条件。

## 先不建大表的最小阶段

1. **冻结现成基线。** 保存现有 Rust Opt9、C H10 程序和源码摘要，固定已有全部 60 条 HTM 15–19 历史输入与顺序；单线程分别运行，禁止两张大表同时驻留。首轮与每进程预热、纯搜索耗时、加载时间、原生最大 RSS、监控树 RSS 分开记账。独立回放每个解并对照已知最短步数；超时或节点预算耗尽记为取消，不能删例后只报成功子集。此阶段只能说明现成两引擎的速度/内存起点，Opt9 表约为 H10 一半，不能宣称已完成 32 GB 档对照。
2. **验证 EO10 坐标，不分配 PDB。** 在现有 407 状态及独立深度 0..3 的 3,502 状态上，核对标量/NEON、正逆状态、u64 地址边界和丢弃新增 EO 位后回到 EO9 的投影关系；补查特殊半转契约。用独立完整 EO 规格交叉核对，不能把复用同一函数两次当作独立 oracle。该有限验证不证明整个抽象状态空间正确，也不证明性能收益。
3. **复现已有小档生成。** 先让纯 Rust 生成器在 Opt1 完整生成相同表，检查保存的 SHA-256、XOR、完整分布和既有状态/搜索验证。再对可控较大已知档位复现，并核对生成日志、前沿容量与实际峰值。所有工作受独占 guard 监控，输出新目录，旧表与失败产物保留。
4. **再进入 EO10 真表阶段。** 先写清抽象投影、距离传播、对称、padding、2-bit 饱和/fallback 编码和下界证明，确定独立的新格式/参数元数据。没有上游 Opt10 golden，应以数学不变量、小空间精确距离、已有档位逐字节复现和独立整解证据组合验证，不能自造 checksum 后将其称为正确性证明。

纯 Rust 生成的工作边界包含生成所需的小查找表、状态/对称/组合映射、fast-move 表、PDB 前沿与距离传播、压缩编码和文件校验；运行时不得调用 WASM、C FFI 或从原版生成器取最终表来冒充原生生成。原 WASM 和已保存表可以继续充当验证参考。纯 Rust 求解、纯 Rust 建表、约 32 GB 档和数学提速是四项独立验收；不能互相替代。
