# 约 32 GB 预算下的 Rust H48 融合计划

状态：2026-10-12 已从计划进入实现：**纯 Rust H10 后端的标量版与优化版均已通过坐标差分和完整固定语料验解，优化版已完成与原 C 的同表、单线程、完整 60 例正式对照**。没有表转换或新表生成。现有 Rust Opt、Nissy C 源码、程序和表均保留；没有替换线上求解器。原始设计与后续 EO10 研究方向保留在下文，最新执行状态见末节和跟踪 MD，性能结果统一见 [性能与内存](benchmark-results.md)。

## 建议

以当前已建立差分验证的 **Rust 搜索内核**为骨架，优先增加纯 Rust 的 **Nissy H10 坐标与读表后端**，直接读取现有有效 H10 文件。这样先得到约 30.34 GB 表预算的可验证实现，无须首先承担另一张 31 GB 新表的生成风险。它不是在 Rust 内继续调用 C 求解器，也不是把 H10 文件交给现有 Opt 解码器。

第二阶段再比较两条数学研究路线：同预算下保留第 10 位 EO 的 Opt 式细投影，或保持 EO9、把空间用于更精确的距离编码/例外修正。以实测决定最终后端；**换语言、更大表、更细投影均不能直接当作加速证据**。

## 两者的共同结构与实际差异

两者属于相近的 H48 投影搜索：角朝向与角 tetrad 分组在 48 对称下得到 **3393 类**，边分为三组四条，共 `C(12,4)×C(8,4)=34650` 个分组，再保留共轭后的部分 EO。两边都有正逆下界、NISS、对侧半转缓存、对称与前缀任务排序。**H10 的 10 指保留 EO 位数，不是最大下界为 10；它现有编码 base=10，非零码为 11/12/13。** Opt9 保留 EO9，其非零码也为 11/12/13。

| 项目 | 现有 Nissy H10 | 当前 Rust Opt9 |
| --- | --- | --- |
| 实际表文件 | **30,336,314,216 bytes**，约 28.253 GiB | **15,565,455,360 bytes**，约 14.496 GiB |
| EO | 11 位共轭 EO 保留高 10 位 | 保留高 9 位，并按 Opt 的位布局插入索引 |
| 物理编码 | 64-byte 行，254 个有效 2-bit 槽，行末 4-bit 最小值 | 16-byte 块，首 4-bit 最小值；每 512 槽表示 495 个边外层状态，包含块头与填充 |
| 零码 | `max(行最小值, EOESEP辅助界)` | 当前仅取块最小值 |
| 额外小表 | COCSEP 同时给出角投影界；EOESEP 给出完整 EO+边分组界 | 原 WASM 小 LUT 用于坐标/对称；当前热路径没有上述独立两级辅助界 |
| 搜索组织 | 每节点批量准备候选子节点、预取正逆表；通常选合法动作较少侧 | 8 个交错 DFS context；按动作数与对侧界选侧；严格同面兄弟剪枝 |
| 前缀/排序 | 固定至 4 步、任务按访问量加面系数排名 | 深度超过编码最大界后逐步扩到 4 步，按双侧界的倒数权重排名 |

H10 主表物理部分为 `64×ceil(117567450×1024/254)=30,334,253,568` bytes；文件另外包含 **2,060,648 bytes** 的三段头部及 COCSEP/EOESEP 数据。它更紧凑的行组织也使零码最小值覆盖更多状态；Opt 小块与 Nissy 辅助 fallback 各有代价，不能只看 EO 位数判断实际界或速度谁占优。

若完全保持 Opt 的坐标布局、填充和两位编码，只从 EO9 扩为 EO10，**主表大小假设**为 `15,565,455,360×2 = 31,130,910,720 bytes`（约 28.993 GiB）。这是尺寸推导，不是已存在的“Opt10”制品；比现有 H10 文件大 794,596,504 bytes。原版仅提供 Opt1～9，现有 Rust 的 Opt 后端也只接受这九档，另有独立的 Nissy H10 后端；自有 EO10 仍需独立坐标/生成规范、base 选择、摘要、分布和正确性验证，不能把最大界自动设成 14。32 GB 是表预算、进程预算还是整机内存也必须分清：以上均不是生成峰值或整机需求。

## 为什么文件不能直接互换

共同的 3393 类与状态计数不等于相同编号。两套 cubie 的块/朝向编码、角代表元编号及对称选择、边分组排名和 EO 位顺序均需显式对应；角对称的不同选择还可能使“丢掉哪一位 EO”不同，未证明映射前不能声称两个实现的投影逐点嵌套。

Nissy 主索引是紧密排列的 `(corner_class×34650 + edge_sep)×2^h + retained_eo`；文件包含三段各 512-byte 的表头，主表再插入每行两个元数据槽。Opt 采用外层 512 槽填充、EO 位插入及另一种块头位置，文件为原始 packed words。即使对齐 cubie，也不能靠换偏移或改长度复用解码。

**可以直接复用的是已有 H10 文件，前提是实现其自己的 Rust 坐标、表头检查与解码。** 首版保持文件不变，不做有损重编码，不用 Opt 的摘要/分布去验证 H10。旧表的固定上游版本与生成边界也属于兼容契约。

## 最小融合边界

后端身份必须显式区分 `Opt(1..9)` 与 `NissyH10`。H10 不登记为上游不存在的 `Opt10`，也不能沿用 Opt 的档位→尺寸公式。表格式、坐标版本、辅助表与摘要随后端绑定；新的本地启动入口需要同步其真实内存预算和守卫范围。

1. **保留一套 Rust 搜索/状态运算，拆开后端。** 原来的 `PruningOracle::lookup(index)` 不能完整表达 H10：零码 fallback 还需要状态的完整 EO+边分组，已折叠主索引不足以恢复它。现已改为关联 `Query` 类型：`prepare(cube, remaining)` 先用 COCSEP 早剪，再保存主索引、角界和转换后的 Nissy 状态；`lookup(query)` 仅零码才计算 EOESEP 坐标。Opt 的 Query 仍为 u64，继续走原坐标与解码。
2. **恢复 H10 的全部有效界。** 正逆两侧都保留便宜的 COCSEP 早剪，以及主表非零 `base+code` / 零码 `max(line_min,eoesep)`。用同一完整状态验证 Opt→Nissy 编号映射，避免热循环里走字符串转换或调用 C。不要只读主表、漏掉辅助界后仍称为等价 H10。
3. **维护半转与 NISS 契约。** 用于现有半转缓存/去半转的组合界必须满足对侧左半转不变性；COCSEP 与 EOESEP 的目标投影可按相同 H48 群作用证明，再做实际坐标差分。完整角排列界等普通 admissible 界应作为独立剪枝，不能混进缓存。参考 `search-invariants.md` 的正逆状态、严格同面阈值与任务所有权条件。
4. **融合数学信息，不同时常驻两张主表。** H10+Opt9 主表相加已约 45.90 GB，超过目标。可复用 H10 的小辅助界改进 Opt 后端：例如对 Opt 零码取 `max(block_min,eoesep)`，理论上逐点不弱；但额外坐标/访问及 NISS 顺序变化意味着实际节点和耗时仍须测。最终选一张主表及必要小表。

## 验证顺序与后续实验

先做纯小状态/查表差分：全部动作及编号映射，原版正逆坐标、半转不变性、两位码/行尾/表头边界，保证 Rust 解码与原版一致；继而在已有 H10 表上验证浅层独立 BFS 和固定已知 HTM 全语料。基准分别固定单线程/8 context 及目标多线程配置，排除加载，保留取消和失败；原 C、Rust H10、Rust Opt 的“节点”定义需先统一才能比较。所有实际计算继续走对应受监控入口，本轮已开始执行这些步骤，实际通过记录以跟踪 MD 和验证报告为准。

新表路线先 profile 真实存活节点上 EO 折叠与 block/fallback 编码分别损失多少下界。仅在相同目标和动作映射下，**精确**投影细化才有 `h_fine≥h_coarse`；重新量化后的界不存在自动支配关系，即便界更强也可能因查表代价及搜索顺序变慢。Nissy 源码已经记录过 base=8 比 base=9 更快的反例。因此 EO10 与 EO9 编码精化应作为同内存的可证伪实验，而非提前宣布优胜。
